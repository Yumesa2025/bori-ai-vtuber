각 항목은 맥락 / 결정 / 근거 / 결과(트레이드오프) 네 단락으로 구성한다.

## ADR-001. 기억 저장소로 SQLite + Prisma 대신 JSON 파일을 쓴다

### 맥락

기획서와 구현계획서는 장기 기억 저장소로 SQLite + Prisma를 명시했다. 실제 구현은 `data/memories.json` 파일 하나와 인메모리 배열이다. **이것은 문서화되지 않은 설계 변경이었고, 이 기록은 그 변경을 사후에 명시하기 위한 것이다.**

기억 시스템에 요구되는 것은 다음이었다. 방송 종료 시 후보 수십 건을 저장하고, 채팅마다 관련 기억 5건을 찾으며, 관리자 화면에 최근 50건을 보여주고, 30일 TTL로 만료시킨다. 접근하는 프로세스는 `apps/server` 하나뿐이다.

### 결정

`packages/memory/src/store.ts`가 프로세스 시작 시 JSON 파일 전체를 읽어 배열에 담고, 변경이 있을 때마다 배열 전체를 다시 직렬화해 덮어쓴다. ORM도 마이그레이션 도구도 쓰지 않는다.

### 근거

- **기억 규모가 작다.** 30일 TTL과 규칙 기반 추출을 감안하면 수백 건 규모다. 전체를 메모리에 올려도 문제가 없고, 인덱스가 필요할 만한 양이 아니다.
- **단일 프로세스가 단독으로 접근한다.** SQLite가 제공하는 트랜잭션·잠금·동시성 제어를 쓸 상황이 없다.
- **스키마가 유동적인 단계였다.** `embedding`, `repeatCount`, `confidence` 필드가 개발 중에 추가됐다. Prisma를 썼다면 각각 마이그레이션 파일이 필요했다. JSON에서는 필드를 선택적으로 선언하고 없으면 `undefined`로 두면 끝난다.
- **의존성이 늘지 않는다.** Prisma는 CLI, 생성 코드, 네이티브 엔진 바이너리를 함께 가져온다. 이 프로젝트는 외부 런타임 의존성을 거의 두지 않는 방향을 택했고(ADR-004, ADR-005), 기억 저장소만 예외로 두기에는 얻는 것이 적었다.
- **검색이 어차피 전체 스캔이다.** 코사인 유사도 계산은 모든 레코드를 순회해야 한다. SQLite를 써도 벡터 검색은 SQL로 표현되지 않으므로 전부 읽어 와야 한다. 저장소를 바꿔도 이 부분은 개선되지 않는다.

### 결과

- **동시 쓰기 안전성이 없다.** 두 프로세스가 같은 파일을 쓰면 한쪽 변경이 사라진다. 현재는 단일 프로세스라 문제가 없지만 이것은 규율이 아니라 전제일 뿐이며, 코드가 강제하지 않는다.
- **원자적 쓰기가 아니다.** `writeFileSync`가 중간에 중단되면 파일이 깨질 수 있다. 임시 파일에 쓰고 rename하는 방식을 쓰지 않았다.
- **전체 로드·전체 저장이라 기억이 커지면 한계가 온다.** 레코드 하나가 바뀌어도 파일 전체를 다시 쓴다. 1536차원 임베딩이 레코드마다 붙으므로 파일 크기가 텍스트 길이보다 임베딩에 지배된다. 레코드 1,000건이면 파일이 수십 MB 규모가 되고, 저장 비용이 눈에 띄기 시작한다.
- **부분 조회가 불가능하다.** 관리자 화면의 "최근 50건"도 전체를 정렬한 뒤 자르는 방식이다.
- **교체 비용은 낮게 유지했다.** `createMemoryStore()`가 반환하는 객체 인터페이스(`load`, `save`, `add`, `search`, `all`, `count`, `remove`, `clear`)만 유지하면 내부를 SQLite로 바꿀 수 있다. 이 파일 하나가 교체 단위다.

## ADR-002. 별도 벡터DB 없이 코사인 유사도를 직접 구현한다

### 맥락

기획서의 원안은 "모든 기억 후보를 불러온 뒤 LLM이 어느 것을 쓸지 선택"이었다. 사전 조사 자료(비공개)에는 게임 지식 RAG용 벡터DB 파이프라인이 있었으나 MVP 범위 밖이었다.

두 방식 모두 그대로 쓰기 어려웠다. 원안은 기억이 늘면 프롬프트가 무한정 길어진다. 벡터DB 도입은 로컬 실행 시스템에 서버 프로세스를 하나 더 붙이는 일이다.

### 결정

임베딩 유사도로 후보를 좁히고, **최종 판단은 답변 LLM이 프롬프트 안에서 한다.** 두 방식을 합친 하이브리드다.

```
score = cosineSimilarity(queryVector, record.embedding) + record.importance * 0.05
```

`minSimilarity`(기본 0.3) 미만을 버리고 상위 `maxMemories`(기본 5)건을 프롬프트의 `[기억]` 섹션에 넣는다. 유사도 계산은 `packages/memory/src/embedding.ts`에 30줄 남짓의 함수로 직접 구현했다.

### 근거

- **기억이 적을 때는 원안과 거의 같게 동작한다.** 임계값 0.3은 낮게 잡은 값이라 레코드가 몇 건뿐이면 대부분 통과한다. 기억이 많아졌을 때 비로소 검색이 실제로 일한다. 규모에 따라 자연스럽게 역할이 바뀐다.
- **최종 선택을 LLM에 맡기는 것은 원안의 장점을 유지하는 선택이다.** 유사도는 "관련 있어 보이는가"만 판단할 수 있고 "이 답변에 실제로 필요한가"는 판단하지 못한다. 후자는 문맥을 읽는 모델이 낫다. 검색기의 역할을 재현율(recall)로 한정하고 정밀도(precision)를 LLM에 넘긴 구조다. 임계값을 낮게 잡은 것도 같은 이유다.
- **1536차원 벡터 수백 개 규모에서 벡터DB는 과잉이다.** 이 정도 규모의 전체 스캔은 밀리초 단위로 끝난다. ANN 인덱스는 데이터가 커져 정확한 계산이 비싸질 때 근사로 바꾸는 최적화인데, 지금은 최적화할 대상이 없다.
- **운영 비용이 0이다.** 로컬 실행 시스템에 별도 서버 프로세스를 띄우면 설치 절차, 포트, 헬스체크, 종료 처리가 전부 사용자 부담이 된다.
- **코사인 유사도는 검증하기 쉬운 코드다.** 길이 불일치와 0 벡터를 처리하는 30줄이고, 외부 의존 없이 정확성을 확인할 수 있다.

### 결과

- **레코드 수에 선형으로 느려진다.** 수천 건까지는 문제가 없지만 수만 건이 되면 채팅마다 전체 스캔이 부담이 된다.
- **검색마다 임베딩 API 호출이 한 번 발생한다.** 질문 벡터를 얻어야 하므로 네트워크 왕복이 응답 지연에 더해진다. 질의 벡터 캐시는 구현하지 않았다.
- **임베딩이 없는 레코드는 사실상 조회되지 않는다.** 점수 0을 받아 임계값 필터에 걸려 탈락한다. 저장은 되었지만 검색되지 않는 기억이 생길 수 있고, 이를 복구하는 재계산 절차는 없다.
- **하이브리드 검색의 표준 기법을 쓰지 않았다.** BM25 같은 키워드 검색과의 결합이나 재순위 모델은 없다. 중요도 가중치 0.05는 타이브레이커일 뿐 진짜 하이브리드 랭킹이 아니다.
- **교체는 가능하다.** `search()` 함수 하나를 바꾸면 되고, `EmbeddingProvider` 인터페이스 덕분에 임베딩 업체 교체도 국소적이다.

## ADR-003. WebSocket 대신 클라이언트 폴링을 쓴다

### 맥락

방송 화면은 서버가 정한 답변·표정·모션·음성을 즉시 반영해야 한다. 관리자 화면은 큐 길이와 LLM 통계를 계속 보여줘야 한다. 시청자 채팅 화면은 보리의 답변을 받아야 한다. "실시간 갱신"이 필요한 클라이언트가 셋이다.

### 결정

`GET /api/state`가 `BroadcastState` 전체를 반환하고, 세 클라이언트가 각각 1초(방송·채팅)와 1.5초(관리자) 간격으로 폴링한다. 서버는 이벤트를 발행하지 않는다.

클라이언트는 이벤트가 아니라 **상태 필드의 변화**로 동작을 결정하고, 마지막 적용값을 `useRef`에 기억해 중복 적용을 막는다(`appliedResponseRef`, `appliedTestSeqRef`, `lastChatIdRef`, `playingMotionRef`, `lastReplyRef`).

명령성 동작인 표정·모션 테스트는 서버가 `lastTestAction.seq`에 단조 증가 번호를 붙여 상태로 표현한다. 같은 버튼을 두 번 눌러도 번호가 달라지므로 두 번째 클릭이 사라지지 않는다.

### 근거

- **재연결 로직이 필요 없다.** WebSocket은 끊김 감지, 지수 백오프 재연결, 재연결 후 상태 재동기화를 구현해야 한다. 폴링에서는 서버가 죽었다 살아나도 다음 1초에 그냥 성공한다. 이 세 가지가 코드에 아예 존재하지 않는다.
- **놓친 이벤트를 따라잡는 문제가 없다.** 매 요청이 전체 스냅샷이므로 새 창을 열면 즉시 올바른 화면이 나온다. 이벤트 스트림이었다면 초기 상태 전송을 따로 설계해야 한다.
- **서버가 클라이언트를 추적하지 않는다.** 연결 목록 관리, 브로드캐스트, 죽은 연결 청소가 전부 불필요하다. `state` 변수 하나만 최신으로 유지하면 된다. 이것이 `apps/server`가 `ws` 의존 없이 `node:http`만으로 끝나는 이유이기도 하다(ADR-004).
- **부하가 무의미한 수준이다.** 127.0.0.1 루프백에서 초당 3회는 측정 대상이 아니다.
- **응답 표시 시간이 5초 이상이라 1초 지연이 문제가 되지 않는다.** 이 시스템의 시간 단위는 사람이 말하는 속도이지 밀리초가 아니다.
- **디버깅이 쉽다.** 브라우저로 `/api/state`를 열면 시스템 상태 전부가 보인다.

### 결과

- **최대 1초의 지연이 항상 존재한다.** 사람 눈에는 문제가 없지만 0은 아니다.
- **폴링 간격보다 짧은 상태는 관측되지 않는다.** 정확성이 "상태가 폴링 주기보다 오래 유지된다"는 암묵적 전제에 의존한다. 현재 값(표시 5초 이상, 응답 간격 5~10초)에서는 여유가 크지만, 관리자가 응답 지연 설정을 1초 아래로 낮추면 조용히 깨진다. **코드에 이 전제를 강제하는 장치가 없다.**
- **아무 일이 없어도 요청이 계속 나간다.** 로컬에서는 비용이 아니지만 원격 배포에서는 그대로 비용이 된다.
- **응답 본문이 매번 전체 상태다.** `visibleChats` 8건을 포함해 매초 전송된다.
- **확장 시 교체가 필요하다.** 클라이언트가 늘거나 서버가 원격으로 가면 SSE 또는 WebSocket으로 바꿔야 한다. 교체 대상은 엔드포인트 하나와 `setInterval` 세 곳이고, 상태 필드 diff 구조는 그대로 재사용할 수 있다. 서버가 이벤트를 밀어 주더라도 ref 기반 중복 적용 방어는 남기는 편이 안전하다.
- **선택의 유효 범위가 좁다.** 이 결정은 "로컬, 클라이언트 3개"라는 전제에서만 옳다. 일반적으로 폴링이 낫다는 주장이 아니다.

## ADR-004. Express/ws 대신 Node 내장 `http`를 쓴다

### 맥락

서버가 제공해야 하는 것은 REST 엔드포인트 15개 남짓이다. 상태 조회, 설정 CRUD, 세션 시작·종료, 채팅 투입, mp3 바이너리 응답, 기억 조회·삭제, Live2D 카탈로그와 테스트.

### 결정

`createServer()` 하나에 `if` 체인으로 메서드와 URL을 직접 검사한다. 라우팅 프레임워크도 미들웨어 계층도 쓰지 않는다.

```
if (request.method === "GET" && request.url === "/api/state") { sendJson(response, 200, state); return; }
```

CORS 헤더와 `Content-Type`은 핸들러 진입부에서 일괄 설정하고, `OPTIONS`는 204로 즉시 응답한다. 본문 파싱은 `request.on("data")`로 문자열을 모아 `JSON.parse`하는 패턴을 필요한 곳마다 반복한다.

### 근거

- **엔드포인트가 15개 수준이라 라우팅 프레임워크의 이득이 적다.** Express가 해결하는 것은 경로 파라미터 추출, 미들웨어 체인, 라우터 분할인데 셋 다 필요가 크지 않았다. 경로 파라미터를 쓰는 곳은 `/api/tts/{id}`와 `/api/memory/{id}` 두 개뿐이고 `startsWith` + `slice`로 충분하다.
- **의존성이 줄어든다.** 이 프로젝트는 Express/ws/Prisma/벡터DB/LLM SDK를 전부 쓰지 않는 방향으로 일관되게 갔다. 로컬에서 사용자가 직접 설치해 실행하는 시스템이라 `npm install` 결과물이 작을수록 좋다.
- **WebSocket이 없으므로 `ws`도 필요 없다**(ADR-003).
- **동작을 전부 눈으로 볼 수 있다.** 미들웨어 순서나 프레임워크의 암묵적 동작에서 오는 문제가 생기지 않는다.
- **Node 내장 API만 쓰면 런타임 업그레이드에 따른 호환성 문제가 적다.**

### 결과

- **수동 `if` 체인은 확장 시 유지보수 비용이 는다.** 순서에 의존하고, 컴파일러가 중복 경로를 잡아 주지 않는다. `startsWith` 기반 매칭은 접두사가 겹치면 앞선 조건이 먹는다. 엔드포인트가 30~40개로 늘면 이 방식은 부담이 된다.
- **본문 파싱 패턴이 5곳 이상 중복된다.** `let body = ""; request.on("data", ...); request.on("end", ...)` 구조가 PATCH·POST 핸들러마다 반복된다. 함수 하나로 추출할 수 있는데 하지 않았다.
- **횡단 관심사를 붙일 자리가 없다.** 요청 로깅, 인증, 레이트 리밋을 추가하려면 각 분기에 직접 넣거나 진입부에 조건문을 늘려야 한다. 현재는 인증이 필요 없어서 문제가 되지 않는다.
- **오류 처리가 각 분기에 흩어져 있다.** `catch { sendJson(response, 400, { error: "Invalid JSON" }); }`가 반복된다.
- **한 파일이 커졌다.** 라우팅이 큐·규칙·세션 로직과 같은 파일(847줄)에 있다. 이 문제는 ADR-012에서 따로 다룬다.

## ADR-005. LLM SDK 대신 `fetch`를 직접 호출한다

### 맥락

OpenAI와 Anthropic 모두 공식 Node SDK를 제공한다. 이 프로젝트가 필요한 것은 단발 요청 하나뿐이다. 구조화된 JSON 응답을 받고, 8초 안에 오지 않으면 포기한다. 스트리밍도, 배치도, 파일 업로드도 쓰지 않는다.

### 결정

`packages/llm/src/openai.ts`와 `anthropic.ts`가 각각 `fetch`를 직접 호출하고, 동일한 `LlmAdapter` 인터페이스를 구현한다.

```
type LlmAdapter = {
  readonly name: string;
  isConfigured(): boolean;
  complete(request: LlmRequest): Promise<LlmRawResult>;
};
```

타임아웃은 `AbortController` + `setTimeout`으로 구현하고, `AbortError`를 잡아 사람이 읽을 수 있는 메시지로 바꾼다. 프로바이더 추가는 `adapterFactories`에 한 줄을 넣는 일이다.

TTS(`tts.ts`)와 임베딩(`packages/memory/src/embedding.ts`)도 같은 방식이다.

### 근거

- **어댑터 경계가 명확해진다.** 각 어댑터가 하는 일이 "요청 본문 조립 → fetch → 응답에서 문자열 추출"로 끝난다. SDK를 쓰면 SDK의 타입과 예외 계층이 어댑터 인터페이스를 넘어 새어 나오고, 어디까지가 이 프로젝트의 계약인지 흐려진다.
- **프로바이더 차이를 드러내는 것이 유리했다.** OpenAI는 `response_format.json_schema(strict)`로, Anthropic은 `tool_choice` 강제 도구 호출로 같은 스키마를 강제한다. 반환 형태도 다르다(문자열 vs 객체). 두 SDK의 추상화를 거치면 이 차이가 각 SDK의 방식대로 가려지는데, 직접 호출하면 차이가 어댑터 안에 그대로 남고 **검증 코드는 하나로 유지된다.** Anthropic 어댑터가 `JSON.stringify`로 객체를 문자열로 되돌리는 것이 그 접합부다.
- **의존성과 설치 크기가 줄어든다.** ADR-004와 같은 판단이다.
- **SDK 버전 변화에 영향받지 않는다.** HTTP API 자체는 SDK보다 안정적이고, 파괴적 변경이 있어도 요청 본문을 고치면 된다.
- **`fetch`가 Node 18 이후 내장이다.** 별도 HTTP 클라이언트도 필요 없다.

### 결과

- **스트리밍 같은 고급 기능은 직접 구현해야 한다.** SSE 파싱, 청크 조립, 부분 JSON 처리가 전부 자체 작업이 된다. 응답 지연을 줄이려면 결국 필요한 기능이라 이 비용은 언젠가 지불하게 된다.
- **재시도와 레이트 리밋 처리가 없다.** SDK가 기본 제공하는 지수 백오프, `Retry-After` 헤더 해석, 429 구분이 전부 빠져 있다. 현재는 회로 차단기가 연속 실패를 흡수하지만, 그것은 재시도가 아니라 포기에 가깝다.
- **토큰 사용량을 집계하지 않는다.** 응답의 `usage` 필드를 읽지 않아 비용 추적이 불가능하다.
- **API 변경을 컴파일러가 잡아 주지 않는다.** 응답 파싱이 `as { choices?: ... }` 형태의 수동 타입 단언이라 필드가 바뀌면 런타임 오류로만 드러난다. 다만 그 뒤에 6단계 검증기가 있어 잘못된 응답이 방송에 나가지는 않는다.
- **Anthropic 어댑터는 실 API 환경에서 검증되지 않았다.** 구조가 실제로 교체 가능한지 보기 위해 만든 두 번째 어댑터이고, OpenAI만 실 API 환경에서 확인했다. 어댑터 경계 설계의 타당성은 확인했지만 Anthropic 경로의 동작은 확인하지 않았다.
- **`gemini`는 타입에만 존재한다.** `adapterFactories.gemini`가 `null`이라 `supportedProviders`에서 자동으로 제외된다. 팩토리 테이블에서 `null`이 곧 "미구현"을 뜻하고 관리자 화면 목록에도 나타나지 않는다. 타입 유니온에 이름만 있는 상태이며 구현 계획은 없다.

## ADR-006. 표정·모션 allowlist를 `packages/live2d`가 단독으로 소유한다

### 맥락

LLM이 결정하는 것은 문장만이 아니다. 감정 이름과 모션 이름도 함께 정하고, 그 이름은 파일 시스템의 표정·모션 자산을 실행하는 식별자가 된다. 모델이 존재하지 않는 이름을 만들어 내면 아무 일도 일어나지 않거나 SDK 내부에서 오류가 난다.

동시에 이 이름들은 구매한 모델에 종속적이다. 파일명은 중국어 병음이고(`xingxingyan`, `kuqi`, `shengqi`, `shoushi` 등), 표정 8종과 모션 4종이 전부다. 모델을 교체하면 전부 바뀐다.

### 결정

허용 목록과 매핑을 `packages/live2d` 한 곳에만 둔다. `boriExpressionNames`(8), `boriMotionGroupNames`(4), `boriEmotionMap`, `boriMotionDescriptions`, `boriMotionLabels`, `motionPairedExpression`, `isBoriExpression`, `isBoriMotionGroup`이 여기에 있다.

**LLM에게 자유 생성을 허용하지 않고 등록된 것 중 선택하게 한다.** 시스템 프롬프트에 허용 감정 목록과 모션 설명을 넣고, 응답은 `validateLlmOutput()`에서 allowlist 대조를 통과해야 한다. 서버는 `POST /api/live2d/test`에서도 같은 판별 함수를 쓴다.

`packages/llm`은 이 패키지를 import하지 않는다. 검증기는 허용 목록을 `LlmRequest.allowedEmotions`·`allowedMotions`로 인자를 통해 받는다.

### 근거

- **모델 자산과 방송 로직을 분리하는 원칙.** 서버는 `happy`, `gaming` 같은 감정 이름만 알고 파일명은 모른다. 방송 화면은 파일명을 알지만 감정이 왜 그렇게 정해졌는지는 모른다. 모델 교체는 `packages/live2d` 한 곳의 수정으로 끝난다.
- **allowlist가 여러 곳에 복사되면 반드시 어긋난다.** 표정 하나를 추가할 때 세 곳을 고쳐야 한다면 언젠가 두 곳만 고치게 된다. 단일 소유자를 두면 이 문제가 구조적으로 사라진다.
- **의존성 역전이 검증기를 재사용 가능하게 만든다.** `packages/llm`이 `packages/live2d`를 import했다면 검증기가 이 모델에 묶인다. 인자로 받으면 다른 캐릭터·다른 모델에도 그대로 쓸 수 있고, 요약처럼 감정·모션이 없는 작업에서 빈 배열을 넘기는 것도 자연스럽다.
- **LLM에게 자유 생성을 허용할 이유가 없다.** 실행 가능한 표정과 모션은 유한하고 이미 알고 있다. 열린 생성은 검증 실패율만 높인다.
- **모션 이름에 한국어 설명을 붙일 자리가 필요했다.** 병음 이름만으로는 모델이 무슨 동작인지 알 수 없어 모션을 거의 고르지 않았다. `boriMotionDescriptions`에 "눈이 별처럼 반짝이는 밝은 표현. 기쁨, 설렘, 신남, 칭찬을 받았을 때, 반가운 인사에 쓴다" 같은 설명을 넣고 프롬프트에 함께 전달하자 선택률이 크게 올랐다. **이 설명이 모델 자산에 대한 지식이므로 allowlist와 같은 곳에 있는 것이 맞다.**

### 결과

- **표현력이 12가지로 제한된다.** 표정 8, 모션 4가 전부이고 세밀한 감정은 표현되지 않는다. 이것은 이 결정의 비용이 아니라 구매 모델의 제약이지만, allowlist 구조가 그 제약을 코드에 고정한다.
- **감정 이름과 모델 자산 사이에 빈 곳이 있다.** `crying`, `angry`, `awkward`는 `boriEmotionMap`에 매핑되어 있지만 그 감정을 내는 규칙이 없어 규칙 응답에서는 나오지 않는다. LLM은 고를 수 있다. `changfa`(긴 머리) 표정은 매핑 어디에도 없어 관리자 테스트 버튼으로만 실행된다. 이것은 캐릭터 설계상의 미결정이지 기술적 미해결이 아니다.
- **모델 교체 시에도 감정 이름 재설계가 필요하다.** 파일명은 이 패키지에 격리되어 있지만, `boriEmotionMap`의 키 집합은 서버 규칙과 LLM 프롬프트가 함께 쓰는 어휘다. 감정 이름 자체를 바꾸면 여러 곳이 함께 움직인다.
- **미사용 스텁이 남아 있다.** `Live2DModelPort` 인터페이스와 `createUnavailableLive2DPort()`는 실제 구현체가 없다. 방송 화면은 SDK 타입을 직접 쓴다. `Live2DModelManifest`의 `physicsFile`도 쓰이지 않는다. 정리 대상이다.
- **`packages/llm/package.json`의 `@bori/live2d` 의존이 실제로는 쓰이지 않는다.** 코드에는 import가 없다. 선언만 남은 상태이고 정리 대상이다.

## ADR-007. 음성 합성을 서버에서만 수행한다

### 맥락

TTS는 브라우저에서 직접 호출할 수도 있다. 방송 화면이 OpenAI `/audio/speech`를 호출해 받은 mp3를 바로 재생하면 서버를 거치지 않아 왕복이 한 번 줄어든다.

문제는 API 키다. 브라우저에서 호출하려면 키가 클라이언트로 내려가야 한다.

### 결정

TTS는 `apps/server`에서만 실행한다. `prepareAudio()`가 `synthesizeSpeech()`를 호출해 mp3 버퍼를 얻고, UUID를 키로 메모리 캐시에 넣은 뒤 상태의 `currentAudioId`에 식별자만 노출한다. 방송 화면은 `GET /api/tts/{id}`로 바이너리를 받는다.

키는 어떤 GET 응답에도 포함되지 않는다. TTS 설정 응답은 `hasApiKey`·`hasElevenLabsKey` 불리언만 담는다.

### 근거

- **API 키가 브라우저로 나가지 않는다.** 방송 화면은 OBS Browser Source로 열리고 시청자 채팅 화면은 LAN에 노출될 수 있다. 키가 클라이언트 번들이나 네트워크 응답에 있으면 그 지점에서 유출된다. 로컬 실행이라 위험이 낮다고 해도, 키를 클라이언트에 두지 않는 것은 비용이 거의 들지 않는 규율이다.
- **ADR-009의 암호화와 일관된다.** 파일에 저장된 키를 암호화하면서 응답으로 평문을 내보내면 앞의 조치가 무의미해진다.
- **캐시와 실패 처리를 한 곳에서 한다.** 30건 캐시, 실패 카운터, 마지막 오류 메시지가 서버에 모여 관리자 화면에 그대로 노출된다.
- **음성 생성 시점을 서버가 통제할 수 있다.** ADR-008의 선합성 방식은 서버가 음성을 만든 뒤 상태를 갱신하기 때문에 성립한다. 클라이언트가 합성하면 이 순서를 만들 수 없다.
- **업체 교체가 클라이언트에 영향을 주지 않는다.** OpenAI와 ElevenLabs 모두 결과를 mp3로 통일했고, 방송 화면은 `/api/tts/{id}`만 안다.

### 결과

- **응답 지연이 1~2초 늘어난다.** 합성 시간과 서버 왕복이 더해진다. 이것이 이 결정의 직접 비용이다.
- **음성 파일이 서버 메모리에만 있다.** 30건을 넘으면 오래된 것부터 버리고, 서버를 재시작하면 전부 사라진다. 방송 화면이 곧바로 받아 가는 데이터라 영속성이 필요 없다고 판단했지만, 다시 듣기나 방송 다시보기가 필요해지면 성립하지 않는다.
- **캐시 축출이 LRU가 아니라 삽입 순서다.** `Map`의 첫 키를 지우므로 정확히는 FIFO다. 방송 흐름상 오래된 음성이 다시 필요할 일이 없어 문제가 되지 않지만, 이름과 실제 동작이 다르다.
- **동일 문장을 재사용하지 않는다.** 규칙 답변은 같은 문장이 반복되는데도 매번 새로 합성한다. 텍스트를 키로 캐시하면 비용과 지연을 줄일 수 있으나 구현하지 않았다.
- **ElevenLabs 경로는 실 키로 검증되지 않았다.** 한국어 캐릭터 목소리 확보 문제로 보류했다. 코드는 있으나 동작을 확인하지 않았다.

## ADR-008. 음성을 먼저 만든 뒤 말풍선을 표시한다 (선합성 방식)

### 맥락

답변이 정해진 뒤 화면에 반영하는 방법은 두 가지다.

1. **선표시** — 말풍선을 먼저 띄우고 음성이 준비되면 재생한다. 자막이 빨리 나온다.
2. **선합성** — 음성을 다 만든 뒤 말풍선과 재생을 함께 시작한다. 소리와 자막이 동시에 시작한다.

### 결정

선합성을 택했다. `scheduleNext()`의 콜백에서 `makeResponse()` 결과를 받은 뒤 `prepareAudio()`를 먼저 완료하고, 그 결과 `audioId`를 `speak()`에 함께 넘긴다.

```
void prepareAudio(responseForChat.reply).then(audioId => {
  if (generation !== sessionGeneration || state.status !== "live") { speaking = false; return; }
  speak(responseForChat, audioId);
});
```

`speak()`가 `currentResponse`와 `currentAudioId`를 **같은 상태 갱신에서** 설정하므로, 방송 화면은 한 번의 폴링에서 둘을 같이 받는다.

### 근거

- **소리와 자막을 동시에 시작시키기 위해서다.** 선표시 방식에서는 말풍선이 먼저 뜨고 1~2초 뒤 소리가 나온다. 이 어긋남은 눈에 잘 띄고, 립싱크가 음성 파형 기반이라 입도 소리와 함께 늦게 움직인다. 자막만 떠 있고 캐릭터는 가만히 있는 구간이 생긴다.
- **폴링 구조와 잘 맞는다.** 두 필드를 한 갱신에 넣으면 클라이언트가 순서를 맞출 필요가 없다. 선표시였다면 "말풍선은 떴는데 audioId가 아직 없는" 중간 상태를 클라이언트가 다뤄야 하고, 상태 필드 diff 구조가 복잡해진다.
- **음성 없이도 그대로 동작한다.** TTS가 꺼져 있거나 실패하면 `audioId`가 `undefined`이고 말풍선만 나간다. 방송 화면은 `currentAudioId` 유무로 파형 립싱크와 사인파 립싱크를 자동으로 전환한다. 폴백 경로가 별도 분기 없이 성립한다.
- **표시 시간 계산에 음성 유무를 반영할 수 있다.** `audioId`가 있으면 `글자수 × 110ms`를 5~15초로 제한한 값을, 없으면 고정 5초를 쓴다. 음성이 끝나기 전에 말풍선이 사라지는 것을 막는다.

### 결과

- **답변까지 1~2초가 더 걸린다.** 이미 5~10초 지연 뒤에 LLM 1.5~2.5초를 기다린 상태에서 추가되는 시간이다. 채팅 투입부터 화면 반영까지 최대 20초 안팎이 될 수 있다.
- **TTS 타임아웃이 15초라 최악의 경우 그만큼 침묵이 길어진다.** 타임아웃 뒤에는 음성 없이 진행되지만, 그 15초 동안 화면에는 아무 일도 일어나지 않는다. 발화권을 이미 잡고 있어 혼잣말도 나오지 않는다. 사용자 입장에서는 시스템이 멈춘 것처럼 보인다.
- **스트리밍 합성으로 바꾸면 지연을 줄일 수 있으나 자막 동기화가 어려워진다.** 첫 청크가 오는 즉시 재생을 시작하면 대기 시간이 크게 줄지만, 서버가 합성 완료 시점을 모르므로 말풍선 표시 시간을 미리 계산할 수 없다. 클라이언트가 재생 진행도를 보고 스스로 결정하는 구조로 바꿔야 하고, 이는 지금의 "서버가 상태를 정하고 클라이언트는 반영만 한다"는 원칙과 충돌한다. 지연 단축과 구조 단순성 사이의 교환이며, 현재는 단순성을 택했다.
- **표시 시간이 글자수 추정값이다.** 실제 음성 길이가 아니라 `글자수 × 110ms`로 계산한다. mp3 duration을 읽지 않으므로 말풍선이 음성보다 먼저 사라지거나 늦게까지 남을 수 있다.

## ADR-009. API 키를 머신 바인딩 키로 암호화해 저장한다

### 맥락

API 키를 넣는 경로는 세 가지다. 환경변수, 관리자 화면 입력, 저장된 설정 파일. 관리자 화면에서 입력한 키는 서버 재시작 후에도 유지되어야 하므로 `data/llm-config.json`, `data/tts-config.json`에 저장된다.

초기 구현은 평문 저장이었다. `data/`는 `.gitignore` 대상이지만, 설정 파일을 실수로 첨부하거나 백업이 유출되면 키가 그대로 노출된다.

### 결정

`apps/server/src/secret-store.ts`가 `AES-256-GCM`으로 암호화한다. 키는 머신 정보에서 파생한다.

```
material = `${userInfo().username}@${hostname()}:bori-ai-vtuber`
key      = scryptSync(material, "bori-secret-salt", 32)
```

저장 형식은 `enc.v1:<iv>:<tag>:<ciphertext>`(각 base64)이다.

접두사가 없으면 이전 버전이 남긴 평문으로 간주해 그대로 읽고, **즉시 암호문으로 재저장한다.** 사용자가 아무것도 하지 않아도 다음 실행에서 파일이 갱신된다.

복호화 실패는 예외로 터뜨리지 않고 빈 문자열을 반환한다. 다른 머신에서 만든 파일이면 "키가 없는 상태"로 동작하고, 경고 로그가 이유를 알려 준다.

### 근거

- **파일 유출과 실수로 인한 공유를 막는다.** 이 시스템의 현실적 위협은 원격 공격자가 아니라 설정 파일이 의도치 않게 다른 곳으로 옮겨지는 상황이다. 머신 바인딩은 그 경우를 정확히 막는다.
- **GCM을 쓰면 변조가 검출된다.** auth tag 검증이 실패하면 복호화가 실패하므로, 잘못된 값이 API 키로 쓰이는 일이 없다.
- **자동 마이그레이션으로 사용자 조작을 없앴다.** 로컬 실행 도구에서 "설정 파일을 지우고 키를 다시 입력하세요"라는 안내는 마찰이 크다.
- **버전 접두사가 향후 교체 경로를 남긴다.** `enc.v2:`를 추가하면 기존 파일을 읽으면서 새 방식으로 넘어갈 수 있다.
- **OS 키체인을 쓰지 않은 이유가 구조적이다.** Electron의 `safeStorage`는 OS 키체인(Windows DPAPI, macOS Keychain)을 사용해 훨씬 강한 보호를 제공한다. 그러나 키를 다루는 것은 `apps/server`이고 이것은 Electron이 아닌 별도 Node 프로세스다. `safeStorage`를 쓰려면 **관리자 앱이 키를 대신 관리하고 서버에 전달하는 구조로 바꿔야 한다.** 그러면 관리자 앱이 항상 켜져 있어야 서버가 동작하거나, 프로세스 간 키 전달 채널을 따로 만들어야 한다. 현재는 그 비용을 지불하지 않고 파일 유출 방지 수준에서 멈췄다.

### 결과

- **위협 모델의 한계가 명확하다. 같은 머신에서 이 코드를 실행할 수 있으면 복호화도 가능하다.** 키 파생 재료가 사용자명과 호스트명이고 salt가 코드에 하드코딩되어 있으므로, 소스를 읽을 수 있는 사람은 `deriveKey()`를 그대로 재현할 수 있다. 저장소가 공개되어 있으니 파생 방식 자체가 공개 정보다. **이것은 로컬 권한 침해를 막는 장치가 아니다.** 이 한계는 코드 주석에도 적혀 있다.
- **사용자명이나 호스트명이 바뀌면 키를 다시 입력해야 한다.** 컴퓨터 이름 변경이나 사용자 계정 변경 후 저장된 키가 풀리지 않는다. 데이터 손실은 아니지만 재입력이 필요하다.
- **메모리에는 평문으로 존재한다.** 복호화된 키가 `llmApiKey` 변수에 프로세스 수명 내내 남는다. 메모리 덤프로부터 보호하는 장치는 없고, 위 한계를 감안하면 추가할 이유도 크지 않다.
- **모든 저장 키가 같은 파생 키를 쓴다.** 키별 분리가 없다.

## ADR-010. 대기 모션을 비활성화한다

### 맥락

Cubism SDK 샘플은 재생 중인 모션이 끝나면 `MotionGroupIdle` 그룹에서 무작위로 하나를 골라 재생한다. 캐릭터가 가만히 있지 않게 하는 표준 동작이다.

구매한 모델에는 모션이 4개뿐이고 전부 `xingxingyan`, `kuqi`, `shengqi`, `shoushi`다. 대기 전용 모션은 없다.

### 결정

`lappdefine.ts`의 `MotionGroupIdle`을 빈 문자열로 두어 대기 모션 재생을 끈다. 대기 중 눈 깜빡임과 호흡은 SDK 기본 동작에 그대로 맡긴다.

### 근거

- **이 모델의 모션 4개는 짝 표정이 켜져 있어야 의미가 있는 효과 애니메이션이다.** 표정 파일이 효과를 켜는 스위치이고 모션 파일이 그 효과의 애니메이션을 돌린다. 표정 없이 모션만 실행하면 화면에 아무 변화가 없다. 즉 이 모션들은 "가만히 있을 때 자연스럽게 움직이는 동작"이 아니라 특정 감정 연출용이다. 대기용으로 쓸 대상 자체가 없다.
- **대기 모션을 켜 두면 응답 모션이 끝나는 즉시 교체되기도 했다.** `startRandomMotion(MotionGroupIdle, PriorityIdle)`이 `_motionManager.isFinished()` 직후에 호출되므로, 감정 표현이 끝나자마자 다른 효과 애니메이션이 들어온다. 짝 표정은 `emotion.durationSeconds` 뒤에 해제되므로 표정과 모션이 어긋나는 구간이 생긴다.
- **눈 깜빡임과 호흡은 별개 경로다.** `CubismEyeBlink`와 `CubismBreath`가 `UpdateScheduler`에서 처리되므로 대기 모션을 꺼도 캐릭터는 정지 화면이 되지 않는다. "가만히 있으면 인형처럼 보인다"는 문제는 대기 모션이 아니라 시선 연출로 해결했다(idle 시 1.1~3.2초마다 무작위 응시).
- **모션 이름이 응답 모션과 겹쳐 상태 추적이 꼬인다.** 방송 화면은 `playingMotionRef`로 재생 중인 모션을 기억해 같은 모션의 중복 실행을 막는다. SDK가 같은 이름의 모션을 대기용으로 임의 재생하면 이 추적이 실제 상태와 어긋난다.

### 결과

- **대기 중 몸 동작이 없다.** 눈 깜빡임, 호흡, 시선 이동만 있다. 대기 전용 모션이 있는 모델이었다면 더 자연스러웠을 것이다.
- **모델 교체 시 재검토가 필요하다.** 이 결정은 이 모델의 자산 구성에서만 옳다. 대기 모션이 별도로 있는 모델이라면 켜는 것이 맞다. `MotionGroupIdle` 상수 하나를 되돌리면 되지만, 그것이 모델 종속적 설정이라는 사실이 SDK 샘플 파일에만 있고 `packages/live2d`에는 없다.
- **SDK 샘플 파일을 수정한 상태다.** `private-assets/`는 저장소 밖이므로 이 설정은 코드로 공유되지 않는다. SDK를 새로 내려받으면 다시 적용해야 한다. `ResourcesPath`, `ShaderPath`, `MotionGroupTapBody`도 같은 파일에서 수정되어 있어 재현 절차가 문서에 의존한다.

## ADR-011. 치지직 실연동을 MVP 범위에서 제외한다

### 맥락

이 프로젝트의 목표는 치지직에서 방송하는 AI 버추얼 스트리머다. 플랫폼 연동이 최종 목적지다.

동시에 검증해야 할 것이 여럿이었다. 채팅 큐가 자연스러운 리듬을 만드는지, 가드레일이 위험 주제를 실제로 막는지, 장기 기억이 대화에 반영되는지, LLM 출력 검증이 잘못된 응답을 걸러 내는지, 립싱크와 표정이 어색하지 않은지.

### 결정

플랫폼 연동을 뒤로 미루고, 세 가지 자체 입력 경로로 먼저 검증한다.

- 관리자 앱의 테스트 채팅 입력
- 방송 화면 우측의 채팅 입력창
- 별도 `chat.html` 시청자 채팅 화면 (다른 창이나 휴대폰에서 접속)

`packages/shared/src/index.ts`의 `ChatSource` 타입에 `"chzzk"` 자리를 미리 만들어 두었다.

```
export type ChatSource = "manual" | "scenario" | "chzzk";
```

**현재 생성되는 값은 항상 `"manual"`이고, 치지직 연동 코드는 존재하지 않는다.**

### 근거

- **플랫폼 연동은 입력 소스 교체 문제이지 코어 로직 문제가 아니다.** 큐, 규칙, LLM, 기억, 렌더링은 채팅이 어디서 왔는지 알 필요가 없다. 새 입력원은 `ChatMessage`를 만들어 큐에 넣기만 하면 된다. 이 경계가 명확하므로 나중에 붙여도 코어가 흔들리지 않는다.
- **검증이 훨씬 빠르다.** 실제 방송을 켜고 시청자가 채팅을 보내기를 기다리는 대신, 특정 문장을 즉시 반복 투입할 수 있다. 가드레일 검증처럼 위험 문장을 일부러 넣어야 하는 작업은 실제 방송에서 할 수 없다.
- **실패의 원인이 명확해진다.** 플랫폼 연동을 먼저 붙이면 문제가 생겼을 때 연동 문제인지 코어 문제인지 구분하는 데 시간이 든다.
- **`chat.html`이 여러 사람이 참여하는 상황도 재현한다.** 휴대폰이나 다른 창에서 접속하므로 닉네임이 다른 여러 시청자를 흉내 낼 수 있다. 실제로 이 경로에서 "기억 검색에 `viewerId` 필터가 없어 다른 시청자의 기억이 섞인다"는 결함이 드러났다.
- **타입에 자리를 만들어 두면 연동 시점의 변경 범위가 드러난다.** `"chzzk"` 값을 실제로 생성하는 코드를 추가할 때 컴파일러가 분기 처리가 필요한 곳을 알려 준다.

### 결과

- **실제 방송 환경에서 검증되지 않았다.** 초당 수십 건이 몰리는 채팅, 도배, 악의적 입력, 긴 방송 중의 메모리 증가를 확인하지 못했다. 30분 이상 장시간 송출 안정성도 미검증이다.
- **`maxQueueSize` 100과 5~10초 응답 간격이 실제 부하에서 맞는지 알 수 없다.** 채팅이 초당 10건씩 들어오면 큐는 10초 만에 가득 차고 대부분 답변되지 못한 채 밀려난다. 선택 알고리즘이 "질문 하나를 앞에서부터 찾기"라 뒤쪽 채팅은 사실상 처리되지 않는다. 현재 입력 경로에서는 이 상황이 재현되지 않는다.
- **`"scenario"` 소스도 미구현이다.** 타입에만 있고 생성하는 코드가 없다.
- **연동 시 새로 필요한 것들이 있다.** 인증 토큰 관리, 연결 유지와 재연결, 플랫폼 이벤트(후원, 구독) 처리, 레이트 리밋 대응은 지금 하나도 없다. "입력 소스 교체"라는 표현은 코어 로직 관점에서 맞는 말이고, 연동 자체가 작은 작업이라는 뜻은 아니다.
- **`duplicateWindowMinutes` 설정이 의미를 갖는 시점이 연동 이후다.** 현재 중복 차단은 세션 내내 무한 누적되는 Set이라 설정과 동작이 불일치한다. 실제 방송에서는 같은 말을 시간을 두고 다시 하는 것이 정상이므로 시간 창이 필요해진다.

## ADR-012. 계획했던 패키지 분리를 하지 않고 로직을 서버에 남겼다

### 맥락

기획서와 구현계획서는 다음 패키지 구조를 명시했다.

```
packages/chat-engine       채팅 큐와 선택
packages/character-engine  응답 생성과 감정 결정
packages/memory-engine     장기 기억
packages/report            방송 리포트
```

실제 구조는 다르다.

```
packages/shared   타입
packages/llm      LLM 어댑터·검증·요약·TTS
packages/memory   장기 기억
packages/live2d   모델 카탈로그·감정 매핑
tools/obs         OBS 자동 설정 (계획에 없던 것)
```

`chat-engine`과 `character-engine`은 만들어지지 않았고 해당 로직이 `apps/server/src/index.ts`에 남았다. `report`는 방송 요약 기능이 `packages/llm/src/summarize.ts`로 축소되어 들어갔다. `memory-engine`은 `memory`로 이름만 바뀌었다.

### 결정

패키지 경계를 **재사용 가능성**이 아니라 **외부 시스템과의 접점**을 기준으로 다시 그었다.

- `packages/llm` — 외부 LLM API와의 접점
- `packages/memory` — 파일 저장소·임베딩 API와의 접점
- `packages/live2d` — 구매 모델 자산과의 접점
- `packages/shared` — 프로세스 경계를 넘는 타입
- `tools/obs` — OBS WebSocket과의 접점

큐·규칙·세션 관리는 접점이 아니라 이 시스템의 고유 로직이라 `apps/server`에 남겼다.

### 근거

- **분리할 이유가 실제로는 없었다.** `chat-engine`과 `character-engine`을 별도 패키지로 두려면 서버가 소비할 인터페이스를 정의해야 한다. 그런데 이 로직들은 `state`, `queue`, `speaking`, `sessionGeneration` 같은 서버의 가변 상태를 직접 읽고 쓴다. 패키지로 빼면 상태를 인자로 전달하거나 콜백으로 주입해야 하고, 실제로 얻는 것은 디렉터리 구분뿐이다. **다른 소비자가 없는 상태에서 재사용을 위한 경계를 만들면 인터페이스만 늘어난다.**
- **접점 기준 분리는 실제 이득이 있었다.** `packages/llm`은 프로바이더가 둘이고 앞으로 늘 수 있어 어댑터 경계가 필요했다. `packages/live2d`는 모델 교체 시 수정 범위를 한정하기 위해 필요했고, 서버·검증기·방송 화면·관리자 앱 네 곳이 참조하므로 실제 다중 소비자가 있다. `packages/memory`는 저장소 구현을 바꿀 여지를 남기기 위해 필요했다.
- **`tools/obs`는 계획에 없었지만 필요해서 생겼다.** OBS 씬과 브라우저 소스를 매번 손으로 설정하는 것이 반복 작업이었다. 캔버스 1920x1080 설정과 소스 트랜스폼 초기화까지 자동화했다. 의존성이 0이라 워크스페이스로 등록하지 않고 `node`로 직접 실행한다. **계획에 없던 것이 추가된 경우이고, 계획 단계에서 예측하기 어려운 종류의 필요였다.**
- **`report`를 별도 패키지로 만들 만한 내용이 없었다.** 방송 요약은 같은 `LlmAdapter`에 프롬프트와 스키마를 갈아 끼우는 75줄 함수로 끝났다. 패키지를 만들면 `packages/llm`에 의존하는 패키지가 하나 늘 뿐이다.

### 현재 평가

**서버 847줄에 큐·규칙·세션·라우팅이 함께 있는 것은 분리 여지가 있다.** 지금 이 파일에는 다음이 섞여 있다.

- 설정 로드·저장 (LLM, TTS, 기억 3종)
- 응답 규칙 테이블과 혼잣말 문장
- 큐 관리와 선택 알고리즘
- 세션 수명과 세대 관리
- 발화권 뮤텍스와 타이머 예약
- HTTP 라우팅 15개 분기

책임이 여섯 가지다. 최소한 다음 셋은 파일을 나눌 만하다.

- **규칙 테이블** — 순수 데이터에 가깝고 서버 상태에 의존하지 않는다. `evaluateByRule()`과 `pick()`은 인자만 받는 함수라 그대로 옮길 수 있다. **테스트를 도입한다면 가장 먼저 대상이 될 부분인데 지금은 서버를 띄우지 않으면 검증할 수 없다.**
- **HTTP 라우팅** — 상태 조작 함수만 호출하면 되므로 별도 파일로 옮길 수 있다. 파일 길이의 절반 가까이가 이 부분이다.
- **설정 로드·저장** — 세 벌의 거의 같은 코드가 반복된다. 경로와 타입만 다르므로 일반화할 수 있다.

세션·큐·발화권은 서로 강하게 얽혀 있어 분리 이득이 작다. 세 가지가 같은 가변 상태를 공유하고 순서에 의존하기 때문이다.

**다만 이것이 "계획대로 패키지를 만들었어야 했다"는 뜻은 아니다.** 필요한 것은 `chat-engine`·`character-engine` 패키지가 아니라 `apps/server` 안에서의 파일 분리다. 패키지 경계를 접점 기준으로 잡은 판단은 유지하되, 서버 내부 구조는 정리 대상이라고 본다.

### 결과

- **계획 문서와 실물 구조가 다르다.** 이 기록이 그 차이를 설명한다.
- **테스트 도입이 어려워졌다.** 규칙 판정과 큐 선택이 모듈 스코프 가변 상태와 얽혀 있어 단위 테스트를 붙이기 어렵다. `packages/llm`의 `validateLlmOutput()`과 `packages/memory`의 `cosineSimilarity()`는 순수 함수라 바로 테스트할 수 있는데, 그것도 패키지로 분리된 덕이다. 현재 이 프로젝트에 자동화 테스트는 하나도 없다.
- **루트 `typecheck` 스크립트가 일부 워크스페이스를 빠뜨렸다.** shared/server/broadcast/admin 4개만 체인하고 live2d/llm/memory 3개는 개별 스크립트로만 존재해 한 번에 전체를 검사하지 못한다. 패키지가 늘어나는 과정에서 루트 스크립트를 함께 갱신하지 않은 결과다.
- **죽은 코드가 남았다.** `apps/admin/src/placeholder.ts`, `createUnavailableLive2DPort()`, `Live2DModelPort`, `packages/shared`의 `topAlert`·`layout`·`emotion.decayStyle`·`emotion.secondary` 필드가 어디서도 쓰이지 않는다. 구조가 계획에서 실물로 옮겨 가는 과정에서 남은 흔적이다.

## ADR-013. 기억에 공개 범위와 소유자를 두고, 소유자를 모르는 기억은 저장하지도 꺼내지도 않는다

### 맥락

기억은 시청자 ID(`viewerId`)와 함께 저장됐지만 검색은 그 값을 보지 않았다. 방송에서 시청자 A가 말한 취향이 B에게 하는 답변 문맥에 그대로 들어갔다. 닉네임 없이 들어온 채팅은 모두 `viewerId: "virtual-viewer"`로 묶였고, 방송 종료 시 추출도 소유자가 없으면 `"virtual-viewer"`를 기본값으로 썼다. **서로 다른 익명 시청자의 기억이 한 사람의 것처럼 섞였다.**

앞으로 1:1 대화 모드가 같은 캐릭터 엔진과 기억 저장소를 쓴다. 방송에서 생긴 기억과 1:1 대화의 개인 기억은 엄격히 분리되어야 한다. 기존 구조에는 "이 기억을 누구에게 답할 때 꺼낼 수 있는가"를 나타낼 자리가 없었다.

### 결정

기억마다 공개 범위 `scope`(`character` / `broadcast` / `private`)와 선택적 소유자 `ownerId`를 둔다. `viewerId`는 없앤다. 파일 형식은 `{ version: 2, records }`다.

검색은 접근 정보를 **필수 인자**로 받는다. 방송이면 `{ mode: "broadcast", speakerId? }`, 1:1이면 `{ mode: "private", userId }`다. 접근 규칙은 다음 표 그대로다.

```
scope      owner     방송(A 발언)  방송(B 발언)  1:1(A)  1:1(B)
character  -         O             O             O       O
broadcast  -(요약)   O             O             X       X
broadcast  A         O             X             X       X
private    A         X             X             O       X
```

- 표에 없는 조합은 모두 막는다. 알 수 없는 `scope`, 소유자가 빈 문자열인 기억, 소유자 없는 `private`, 소유자가 붙은 `character`가 여기에 든다.
- 필터는 유사도 순위와 임베딩 없는 폴백 정렬 **둘 다보다 먼저** 건다.
- 익명 채팅(`virtual-viewer`)은 `speakerId` 없이 검색한다. 소유자 없는 방송 기억과 캐릭터 기억만 본다.
- 익명 발언에서는 기억 후보를 만들지 않는다.
- 같은 문장이라도 `scope`나 소유자가 다르면 별개의 기억으로 둔다.
- 방송 기억은 1:1에서 쓰지 않는다. 방송 시청자와 1:1 사용자를 잇는 계정 연동은 이번 범위가 아니다.

기존 파일은 서버가 처음 읽을 때 옮긴다.

| 예전 기록 | 옮긴 결과 |
|---|---|
| `kind: "broadcast"`, `viewerId` 없음 | `scope: "broadcast"`, 소유자 없음 |
| `viewerId`가 `local:`로 시작 | `scope: "broadcast"`, `ownerId = viewerId` |
| 그 밖(`virtual-viewer`, 처음 보는 접두사, `viewerId` 없는 시청자 기억) | **삭제** |

옮기기 전에 원본을 `memories.v1-backup-<시각>.json`으로 같은 디렉터리에 그대로 남기고, 변환·삭제 건수를 로그로 남긴다. 옮긴 파일은 `version: 2`라 다시 읽어도 바뀌지 않는다.

### 근거

- **누구의 것인지 모르는 기억은 꺼내지 않는 쪽이 안전하다.** 기억을 놓치면 답이 조금 덜 개인적일 뿐이다. 남의 기억을 꺼내면 개인정보가 다른 시청자 앞에서 방송 화면으로 나간다. 두 실패의 비용이 비대칭이라 fail closed를 택했다.
- **필터를 순위 계산 뒤에 걸면 결과가 틀린다.** top-K를 먼저 자르고 거르면 남의 기억이 자리를 차지해 본인 기억이 밀려나거나 아무것도 남지 않는다. 폴백 경로는 임베딩이 없을 때만 타므로 평소에 눈에 띄지 않는다. 두 경로 모두 단위 검사로 고정했다.
- **접근 정보를 선택 인자로 두면 빠뜨린다.** 기본값이 "전체 허용"이면 새 호출 지점 하나가 격리를 깬다. 필수 인자로 두면 타입 검사가 빠뜨린 곳을 잡는다.
- **`virtual-viewer` 기억은 고칠 방법이 없다.** 원래 누가 말했는지 정보가 이미 사라졌다. 소유자 없는 방송 기억으로 바꾸면 한 시청자의 취향이 모두에게 열리므로 그것도 격리 위반이다. 지우는 것이 유일하게 안전한 처리이고, 사용자가 이 정책을 확정했다. 되돌릴 수 있도록 백업을 남긴다.
- **익명 발언을 저장하지 않으면 같은 문제가 다시 생기지 않는다.** 마이그레이션으로 한 번 지워도 추출이 계속 `virtual-viewer`로 저장하면 다음 방송에서 다시 섞인다.

### 결과

- **기존 기억 일부가 사라진다.** 닉네임 없이 쌓인 시청자 기억은 모두 지워진다. 백업 파일에는 남지만 서버가 다시 읽지는 않는다.
- **익명 시청자는 기억되지 않는다.** 닉네임을 입력하지 않은 시청자의 취향은 다음 방송으로 이어지지 않는다.
- **시청자 식별이 닉네임 기반이다.** 인증이 없으므로 같은 닉네임을 입력한 다른 사람은 그 시청자의 기억을 문맥으로 끌어낼 수 있다. 플랫폼 계정 ID를 쓰기 전까지의 한계다.
- **1:1 개인 기억은 스토어 지원만 있다.** `private` 저장·검색 규칙과 소유자별 삭제(`removeByOwner`)는 준비되어 있으나 만드는 경로는 1:1 모드와 함께 들어온다(Phase 4).
- **백업 파일이 남는다.** 마이그레이션은 한 번만 일어나므로 파일도 하나지만, 지우는 것은 사용자 몫이다. 백업에는 지운 기억의 원문이 그대로 있다.

## ADR-014. 공통 대화 엔진을 서버 내부 모듈로 두고, 방송 재시작은 세션 객체 교체로 처리한다

### 맥락

1:1 대화(companion) 모드는 방송과 같은 캐릭터·응답 경로를 쓰되 대화 기록과 개인 기억을 엄격히 나눠야 한다. 그런데 응답 생성(`makeResponse`)과 문맥 기록(`recordTurn`)은 `apps/server/src/index.ts`의 모듈 전역 상태를 직접 읽고 썼다. `recentTurns`·`sessionTurns`·누적 요약·`activeMacros`·`replyLastUsedAt`가 프로세스에 한 벌뿐이라 두 번째 대화를 만들 방법이 없었고, LLM 실패 시에는 응답 함수가 방송 상태(`state.lastError`)를 직접 고쳤다.

누적 요약은 비동기로 늦게 도착한다. 요약을 기다리는 사이 방송을 다시 시작하면 이전 방송의 요약이 새 방송에 써지지 않도록, 요약 콜백이 방송 세션 세대(`sessionGeneration`)를 비교했다. 문맥 관리가 방송 타이머용 장치에 묶여 있던 셈이다.

### 결정

- 엔진은 `apps/server/src/conversation/`에 둔다. 패키지(`packages/conversation`)로 빼지 않는다.
- 대화별 상태는 `ConversationSession` 객체 하나에 모은다. `createSession(mode)`가 만들고, 이때 `packages/character`의 모드 정책을 세션에 고정한다. 방송은 방송 시작마다, 1:1은 사용자별로 만든다.
- 엔진의 공개 동작은 `respond(session, input)`(위험 차단 → 규칙 → 매크로 → 기억 검색 → LLM → 검증 → 폴백), `record(session, turn)`(턴 기록 + 누적 요약 트리거), `tickMacros`·`clearMacros`, `pickReply`, `systemPromptChars`다.
- `respond`는 `{ kind: "blocked" } | { kind: "reply"; response; failure? }`를 돌려준다. 엔진은 `BroadcastState`를 모르고, `state.lastError` 갱신은 결과를 받은 방송 쪽이 한다.
- 기억 검색은 엔진 안에서만 한다. 모드와 `speaker.ownerId`로 접근 범위를 정한다. 방송은 `{ mode: "broadcast", speakerId }`(익명이면 `speakerId` 없음), 1:1은 `{ mode: "private", userId }`이고 1:1에서 소유자를 모르면 검색하지 않는다.
- 누적 요약의 세대 검사는 **세션 객체 교체**로 대신한다. 요약 결과는 호출할 때 잡아 둔 세션 객체에 쓴다. 방송을 다시 시작하면 방송 쪽이 새 세션을 만들므로 늦게 도착한 요약은 버려진 옛 세션에 써질 뿐이다.
- 큐·중복 창·발화권·응답/혼잣말 타이머·세션 세대·`BroadcastState`·혼잣말·방송 상황 문장·방송 종료 시 기억 저장은 방송 쪽(`index.ts`)에 남긴다. `speak`·`scheduleNext`·혼잣말의 세대 검사도 그대로 둔다.
- LLM 클라이언트·설정·키·기억 저장소·임베딩·매크로 정의·문장 쿨다운 값은 엔진을 만들 때 주입한다. 관리자 화면에서 바뀌는 값은 getter로 넘겨 매번 최신 값을 읽는다. LLM 클라이언트는 `llmFor(mode)` 한 곳으로 받아, 모드별 인스턴스로 나눌 때 이 함수만 바꾸면 되게 했다.

### 근거

- **소비자가 서버 하나다.** 방송과 1:1 모두 같은 서버 프로세스가 처리한다. 두 번째 런타임이 없는데 패키지로 빼면 인터페이스만 늘어난다(ADR-012와 같은 판단).
- **기억 파일의 작성자가 하나여야 한다.** 저장소는 파일을 통째로 덮어쓴다. 엔진이 패키지가 되어 다른 프로세스에서 쓰이면 두 작성자가 서로의 기록을 지운다. 서버 내부에 두면 그 경로가 처음부터 없다.
- **세대 번호보다 객체 교체가 경계가 분명하다.** 세대 번호는 방송 하나에만 있는 값이라 1:1 세션의 요약까지 방송 재시작에 휩쓸린다. 요약이 자기 세션 객체에만 쓰면 재시작이든 1:1 세션 여러 개든 같은 규칙으로 격리된다. 타이머와 화면에 관한 세대 검사는 방송 고유의 제약이라 방송 쪽에 남겼다.
- **실패 보고를 결과로 돌려주면 모드마다 다르게 처리할 수 있다.** 방송은 관리자 화면의 `lastError`에 쓰고, 1:1은 다른 곳에 알릴 수 있다. 엔진이 방송 상태를 직접 고치면 1:1 실패가 방송 관리 화면에 나타난다.
- **검색을 엔진 안으로 모으면 접근 범위를 빠뜨릴 곳이 하나뿐이다.** 서버 다른 곳에 `memoryStore.search` 호출이 없으므로, 새 모드도 `memoryAccessFor`를 거쳐야만 기억을 읽는다.

### 결과

- **방송 동작은 그대로다.** 통합 검사 46건이 검사 파일 수정 없이 통과했다. 시스템 프롬프트와 `systemPromptChars` 값도 같다.
- **요약 진행 표시(`summaryInFlight`)가 세션마다 따로다.** 예전에는 전역 하나라, 이전 방송의 요약이 진행 중이면 새 방송의 첫 요약이 그 응답을 기다렸다. 지금은 새 방송이 바로 자기 요약을 시작할 수 있다. 끝난 방송의 요약이 늦게 오면 그 세션에 써지지만 아무 데서도 읽지 않는다.
- **방송 상황 문장을 계산하는 시점이 조금 앞당겨졌다.** 예전에는 기억 검색이 끝난 뒤 계산했고, 지금은 방송 쪽이 `respond`를 부를 때 계산해 넘긴다. 차이는 기억 검색 시간만큼이며 경과 분 단위 표시에만 영향이 있을 수 있다.
- **1:1 세션도 방송 규칙 문장을 쓴다.** 규칙·폴백 문장에 "여러분" 같은 방송 호칭이 들어 있다. 1:1 전용 문장은 아직 정해지지 않은 설정이라 이번에 만들지 않았다(검토 필요). 1:1 API(Phase 4)에서 모드별 문장 세트를 정해야 한다.
- **엔진 단위 검사를 서버 안에 둔다.** `apps/server/test/*.test.ts`를 루트 `npm run test:unit`이 함께 돌린다.

## ADR-015. 로컬 API 보안 경계를 토큰 대신 Origin·Host·Content-Type 조합으로 세운다

### 맥락

서버는 `127.0.0.1`에만 바인딩하지만 모든 응답에 `Access-Control-Allow-Origin: *`를 붙였다. 사용자가 브라우저로 연 아무 웹사이트나 `http://127.0.0.1:4310`에 요청을 보내 응답을 읽을 수 있었다. 본문은 Content-Type과 상관없이 파싱했으므로, 사전 요청(preflight)이 없는 `text/plain` 폼 POST로 방송을 시작·종료하거나 설정을 바꿀 수도 있었다(CSRF). 브라우저가 공격자 도메인을 `127.0.0.1`로 다시 풀게 하는 DNS rebinding이면 같은 출처로 취급되어 Origin 검사조차 피한다.

곧 개인 대화 API(`/api/conversations`, `/api/me/memories`)가 같은 서버에 붙는다. 1:1 사용자는 로컬 단일 사용자이고(인증 없음) 서버는 루프백 바인딩을 유지한다는 전제가 확정됐다.

클라이언트는 방송 화면·채팅 화면(4173, preview 4174), 1:1 화면(4175, preview 4176), 관리자 렌더러(5174, Electron이 같은 주소를 연다)이며 모두 Vite 프록시를 거쳐 상대 경로 `/api`로 부른다. 통합 검사와 평가 도구는 Origin 없이 직접 부른다.

### 결정

`apps/server/src/http/guard.ts`의 `guardRequest`를 `createServer` 핸들러 맨 앞에서 한 번 부른다. 이후에 붙는 라우트도 자동으로 같은 검사를 받는다.

- **Host**: 호스트명이 `127.0.0.1`·`localhost`·`[::1]`이 아니면 421. 포트는 보지 않는다.
- **Origin**: 헤더가 있으면 허용 목록만 통과하고 나머지는 403. 헤더가 없으면 통과한다. 허용된 Origin에는 `*` 대신 그 Origin을 돌려주고 `Vary: Origin`을 붙인다. 기본 목록은 위 클라이언트 포트의 `http://127.0.0.1:*`와 `http://localhost:*` 10개이고, `BORI_ALLOWED_ORIGINS`(쉼표 구분)로 덧붙인다.
- **Content-Type**: 본문이 있는 POST·PATCH·PUT은 `application/json`만 받는다(415). 본문 없는 POST(`/api/session/start` 등)는 Content-Type 없이 받되 Origin 검사는 똑같이 거친다.
- **본문 크기**: 64KB. 선언된 길이가 넘으면 읽지 않고 413, 길이를 선언하지 않은 본문은 `readBody`가 읽는 도중 413으로 끊는다. 넘친 본문은 쌓지 않는다.
- **설정 검증**: `PATCH /api/settings`·`/api/memory`·`/api/tts`는 키 허용 목록·타입·범위를 검사하고, 하나라도 틀리면 아무것도 병합하지 않고 400을 돌려준다.

### 근거

- **브라우저가 위조할 수 없는 헤더만 믿는다.** Origin과 Host는 웹 페이지의 스크립트가 바꿀 수 없다. 교차 출처 요청에서 응답을 읽으려면(CORS) 또는 POST를 보내려면 브라우저가 반드시 Origin을 붙인다. Origin이 없는 요청은 브라우저 밖의 프로세스이고, 그 프로세스는 이미 이 컴퓨터에서 코드를 실행하고 있으므로 이 경계로 막을 대상이 아니다.
- **DNS rebinding은 Origin으로 못 막고 Host로 막는다.** 재바인딩된 페이지는 같은 출처라 GET에 Origin을 붙이지 않지만, Host 헤더에는 공격자 도메인이 남는다.
- **Content-Type 제한은 사전 요청을 강제한다.** `application/json`은 단순 요청(simple request)이 아니므로 다른 출처가 보내려면 사전 요청을 거쳐야 하고, 그 단계에서 Origin 검사에 걸린다. Origin 검사가 어떤 이유로 빠져도 폼 POST로는 상태를 바꿀 수 없게 하는 이중 장치다.
- **토큰을 택하지 않았다.** 클라이언트가 같은 머신의 정적 페이지라 토큰을 숨길 곳이 없다. 페이지에 심으면 그 페이지를 여는 누구나 읽고, 서버가 발급하면 발급 엔드포인트를 다시 Origin으로 지켜야 한다. 단일 사용자·루프백 전제에서는 토큰이 지키는 범위가 Origin·Host 조합과 같으면서 클라이언트 세 곳과 테스트 도구를 모두 고쳐야 한다. 외부 공개나 다중 사용자로 전제가 바뀌면 인증을 따로 붙여야 하며, 이 경계는 그때도 그대로 둔다.
- **Vite 프록시는 Origin을 그대로 넘기고 Host를 바꾼다.** 실제로 확인했다. 프록시 설정이 문자열 축약형이라 `changeOrigin: true`가 되어 Host가 `127.0.0.1:4310`으로 바뀌고, Origin은 브라우저가 보낸 값(`http://127.0.0.1:4173` 등)이 그대로 온다. 그래서 Host는 호스트명만 보고, Origin 허용 목록은 프록시 앞의 클라이언트 주소로 만든다. Vite 6.4 dev 서버는 자체적으로 낯선 Host를 403으로 막으므로 프록시 앞단의 rebinding도 막힌다.

### 결과

- **기존 클라이언트는 고치지 않았다.** 본문을 보내는 호출은 모두 이미 `Content-Type: application/json`을 붙이고 있었고, 본문 없는 POST는 그대로 통과한다. 방송 화면 dev 서버(4173)와 관리자 렌더러(5174)를 실제 브라우저로 열어 프록시 경유 GET·POST·PATCH가 통과하는 것을 확인했다.
- **허용 목록 밖에서 여는 클라이언트는 설정이 필요하다.** 휴대폰에서 LAN IP로 `chat.html`을 열면 Origin이 `http://192.168.x.x:4173`이 되어 채팅 POST가 403이 된다. `BORI_ALLOWED_ORIGINS`에 그 주소를 넣어야 한다(운영 가이드 1절). 관리자 렌더러 주소를 `BORI_ADMIN_URL`로 바꿨을 때도 같다.
- **Origin이 `null`인 요청은 막힌다.** `file://`로 연 페이지나 샌드박스 iframe이 해당한다. 이 저장소에는 그런 클라이언트가 없다.
- **설정 범위가 서버에 생겼다.** 예전에는 음수 대기 시간이나 문자열 숫자도 저장됐다. 범위는 관리자 화면 입력 제약과 기본값, 통합 검사가 쓰는 값(혼잣말 간격 2초, 중복 창 0분)을 모두 받도록 정했다. 최솟값이 최댓값보다 크면 거부한다(예전에는 조용히 최솟값으로 맞췄다).
- **`PATCH /api/llm`은 아직 키 허용 목록 검사가 없다.** 업체 검사와 요약 주기 하한만 있다. 이번 범위는 큐·기억·음성 설정이며 LLM 설정 검증은 후속 작업이다.
- **새 라우트가 본문을 직접 모으면 길이 미선언 본문의 상한이 빠진다.** 선언된 길이는 가드가 막지만, 청크 전송은 `readBody`를 써야 끊긴다. 새 라우트는 `readBody`로 본문을 읽는다.

## ADR-016. 1:1 대화를 JSON 파일 저장소에 소유자별로 두고, LLM 회로와 통계를 모드별로 나눈다

### 맥락

Phase 4에서 1:1 대화(companion) API를 연다. 대화와 메시지는 서버를 다시 띄워도 남아야 하고, 방송 상태·큐·방송 세션과는 섞이지 않아야 한다. 사용자는 로컬 단일 사용자이고 서버가 소유자 ID `companion:local`을 정한다(클라이언트는 정할 수 없다).

LLM 클라이언트(`createLlmClient`)는 회로 차단기와 호출 통계를 안에 갖는다. 방송과 1:1이 하나를 같이 쓰면 1:1에서 연달아 실패한 것만으로 방송 회로가 열려 방송이 폴백 문장으로 떨어진다. ADR-014에서 `llmFor(mode)` 주입점만 만들어 두었다.

사용자 결정으로 1:1은 규칙 응답(인사·칭찬 등 방송 고정 문장)을 쓰지 않고 LLM이 답한다. 위험 주제는 그대로 막되 방송처럼 무반응하지 않고 짧게 거절한다.

### 결정

- **저장소**: `apps/server/src/companion/store.ts`. `BORI_DATA_DIR`(기본 `data/`) 아래 `companion-conversations.json` 파일 하나에 `{ version, conversations, messages }`를 둔다. ADR-001처럼 통째로 읽고 쓴다.
- **소유자**: 대화와 메시지 레코드 모두 `ownerId`를 갖고, 조회·추가·삭제는 항상 소유자로 거른다. 남의 대화는 404와 구분하지 않는다. 응답에는 `ownerId`를 싣지 않는다. 읽을 때 소유자가 없는 레코드는 버린다.
- **원자적 쓰기**: 임시 파일에 쓰고 `fsync`한 뒤 `rename`으로 바꾼다. 쓰기가 성공했을 때만 메모리 상태를 바꾼다. 읽을 수 없는 파일은 지우지 않고 `*.unreadable-<시각>.json`으로 백업한 뒤 빈 상태로 시작한다.
- **세션**: 대화마다 `createSession("companion")` 세션을 메모리에 두고 처음 쓸 때 만든다. 만들 때 저장된 최근 메시지로 최근 대화를 되살린다(`engine.restore`). 거절한 대화(차단 입력과 거절 문장)는 되살리지 않는다. 답변을 저장한 뒤에만 `record`·`tickMacros`를 부르고, 대화를 지우면 세션도 버린다. 같은 대화에 답변을 만드는 중이면 409로 돌려보낸다.
- **정책 분기**: `ConversationPolicy`에 `ruleReplies`·`refusalReplies`·`fallbackReplies`를 둔다. 엔진은 이 값으로 규칙 사용 여부, 차단 시 거절 문장(`blocked.refusal`), 폴백 문장을 정한다. 방송 값은 `ruleReplies: true`, 거절 없음, 서버 폴백 문장으로 기존 동작과 같다. 1:1 거절·폴백 문장은 `packages/character`에 초안으로 두고 `검토 필요`로 표시한다. 규칙을 쓰지 않는 모드는 LLM을 못 쓰는 경우(꺼짐·키 없음·회로 열림)도 `failure`로 알린다.
- **LLM 회로 분리**: `createModeLlmClients`가 모드마다 `createLlmClient()`를 하나씩 만든다. 관리자 `/api/llm`의 `status`는 방송 것이고 1:1은 `companionStatus`로 따로 보여 준다. 설정을 바꿀 때의 reset은 두 클라이언트에 함께 적용한다.
- **개인 기억**: 사용자 메시지를 저장할 때 `extractPrivateMemoryCandidates`로 후보를 뽑아 `scope: "private"`, `ownerId: companion:local`로 저장한다. 방송 추출과 같은 규칙을 쓰고 공개 범위와 소유자만 다르다. 차단한 입력은 후보로 만들지 않는다. 저장은 답변 생성과 나란히 돌리고, 실패해도 답변은 나간다.
- **라우트**: `index.ts`에는 처리기 한 줄만 둔다. 경로 판정은 동기로 하고 응답은 모듈 안에서 비동기로 보낸다. 방송 상태·큐·방송 세션은 이 모듈에 넘기지 않는다.
- **본문 읽기**: 1:1 라우트의 본문은 `companion/body.ts`의 `readBody(request, response, onBody)` 하나로 읽는다. API 보안 작업의 `readBody`와 시그니처·상한(64KB, 초과 413)이 같아 병합할 때 그쪽 함수로 바꿔 끼운다.

### 근거

- **넘기지 않은 것에는 닿을 수 없다.** 1:1 모듈의 의존성에 `state`·큐·`broadcastSession`이 없으므로 1:1 요청이 방송 화면이나 방송 문맥을 바꿀 경로가 코드에 없다. 음성도 `prepareAudio`만 받아 방송 `currentAudioId`에 쓰지 않는다.
- **파일 하나가 목록과 메시지의 일관성을 지킨다.** 대화 목록의 `messageCount`·`updatedAt`과 실제 메시지를 다른 파일에 두면 쓰기 사이에 멈췄을 때 어긋난다. 로컬 단일 사용자 규모에서는 통째로 쓰는 비용이 작다.
- **회로는 장애 범위를 나누는 장치다.** 1:1 실패가 방송을 멈추면 회로 차단기가 오히려 장애를 퍼뜨린다. 클라이언트를 나누는 것이 가장 작은 변경이었다(ADR-014의 주입점).
- **정책을 데이터로 두면 방송 분기가 한 곳에 모인다.** 엔진 안에 `mode === "companion"` 조건을 흩어 두지 않고 정책 값으로 분기하므로, 방송 값이 그대로면 방송 동작도 그대로다.

### 결과

- **대화를 지워도 그 대화에서 생긴 개인 기억은 남는다.** 기억은 대화가 아니라 사용자 소유다. 개인 기억은 `GET/DELETE /api/me/memories`로 따로 보고 지운다.
- **관리자 `/api/memory`에는 1:1 개인 기억도 보인다.** 관리자 원문 열람은 기존 원칙(ADR-013)을 따른다. 관리자 화면의 1:1 통계·기억 표시는 후속이다.
- **1:1 대화의 누적 요약이 방송용 요약 프롬프트를 쓴다.** `summarizeSessionProgress`의 지시문이 "방송"·"시청자" 기준이다. 결과는 그 1:1 세션에만 쓰이므로 격리 문제는 없지만 요약 품질은 미검증이다. 모드별 요약 지시문은 후속이다.
- **되살린 최근 대화는 아직 요약되지 않은 것으로 남는다.** 재시작 뒤 대화가 이어지면 다음 누적 요약 때 함께 접힌다. 최근 대화 창(10턴)보다 앞선 내용은 재시작으로 문맥에서 빠진다.
- **ADR-014의 "1:1 세션도 방송 규칙 문장을 쓴다"는 해소됐다.** 1:1은 규칙 문장을 쓰지 않고, 거절·폴백도 1:1 전용 초안 문장을 쓴다.
- **ADR-001의 한계 중 동시 쓰기 안전성 없음은 그대로다.** 단일 프로세스 전제에 기댄다. 원자적 쓰기는 이 저장소에만 적용했고 기억 저장소(`memories.json`)는 여전히 덮어쓴다.

# 진행 현황

최종 갱신: 2026-10-12 · 프로젝트 기간: 2026.06 ~ 진행 중

로컬 실행형 AI 버추얼 스트리머 "보리"의 구현 현황이다. 규칙 응답, Live2D 표정·모션, 시선, 립싱크, 외부 LLM, 장기 기억, TTS, OBS 송출까지 하나의 파이프라인으로 연결되어 동작한다. 치지직 실제 채팅 연동은 MVP 범위 밖이며, 방송 화면과 별도 채팅 화면의 수동 입력이 그 역할을 대신한다.

이 문서가 진행 상황의 **단일 기준**이다. 완료 여부, 검증 여부, 남은 작업에 대해 다른 문서와 서술이 충돌하면 이 문서를 따른다.

## 1. 완료된 기능

아래 항목은 구현이 끝났고 수동 검증 또는 자동 검사로 동작을 확인한 것이다. 자동 검사(단위·통합)만으로 확인하고 실 API로는 확인하지 않은 항목은 그렇게 따로 적었다. 검증 요약은 4절, 상세 항목은 [검증 기록](./verification-log.md)에 있다.

### 1.1 기반 구조

- npm workspaces 모노레포. `apps/server`, `apps/broadcast`, `apps/admin`, `packages/{shared,live2d,llm,memory,character}`, `tools/obs`, `tools/test`
- 서버는 `node:http`만 사용한다. Express·ws·ORM·벡터DB·LLM SDK 등 런타임 의존성이 없다
- `packages/*`는 빌드 없이 TS 원본을 직접 참조한다
- 공용 타입 전용 패키지 `packages/shared` 분리
- 루트 `npm run typecheck`가 8개 워크스페이스 전부를 검사한다. 단위 검사는 `npm run test:unit`(`packages/*/test/*.test.ts`, `node:test` + `tsx`), 통합 검사는 `npm run test`(`tools/test`)다
- 프로덕션 빌드 지원. SDK 샘플을 Vite 별칭으로 번들에 포함하고, 비공개 자산을 dev와 빌드가 동일한 URL 구조로 서빙한다

### 1.2 실시간 통신

- **WebSocket·SSE를 쓰지 않는다.** 클라이언트가 `GET /api/state`를 주기적으로 폴링한다 (방송 화면 250ms, 채팅 화면 1초, 관리자 1.5초)
- 이벤트 버스가 아니라 **상태 필드 diff**로 동작한다. `currentResponse`, `currentAudioId`, `lastTestAction.seq`, `visibleChats`, `status`를 비교해 변화를 감지한다
- 클라이언트가 마지막 적용값을 ref로 기억해 같은 응답이 반복 수신되어도 한 번만 적용한다

### 1.3 방송 화면

- 1920x1080 가로형 레이아웃. 중앙 캐릭터 영역 + 우측 익명 채팅 패널
- 채팅 최대 8개 표시, 최신 채팅이 아래에 쌓이는 구조, 자동 스크롤
- 답변 말풍선 표시와 종료 후 자동 제거. 음성이 있으면 표시 시간을 답변 길이에 맞춰 늘린다
- 우측 하단 채팅 입력창. `?input=0` 파라미터로 숨겨 OBS 송출용으로 쓴다
- 출력 대상은 **OBS Browser Source 전용**이다. Electron 방송 창은 지원하지 않는다
- 모델 로드 실패 시에만 진단 배지를 노출한다

### 1.4 시청자 채팅 화면

- 별도 진입점 `chat.html`. 다른 브라우저 창에서 열어 시청자처럼 채팅한다. 서버·dev·preview가 모두 `127.0.0.1`에 바인딩되어 휴대폰이나 다른 기기에서는 열 수 없다(3.1절)
- 닉네임 입력과 로컬 저장, 방송 상태·서버 연결 상태 표시, 방송 중이 아닐 때 전송 차단
- 닉네임은 내부 `viewerId`로만 사용하고 방송 화면 채팅 목록에는 내보내지 않는다. `/api/state`의 `visibleChats`는 `VisibleChat` 타입(`id`·`content`·`receivedAt`·`category`)만 실어 닉네임에서 만든 `viewerId`도 나가지 않는다. 통합 검사 2건이 확인한다
- 닉네임이 있는 시청자의 기억은 그 시청자의 내부 ID(`local:닉네임`)를 소유자로 저장한다. 닉네임 없는 익명 채팅(`virtual-viewer`)은 기억으로 남기지 않는다
- 답변 문맥에는 말한 시청자 본인의 기억과 소유자 없는 방송 기억만 들어간다. 다른 시청자의 기억은 검색 단계에서 빠진다 (1.12절 참조)

### 1.5 관리자 앱

- Electron 창 + React UI. 로드 실패 시 자동 재시도, 렌더러 콘솔 로그 파일 기록
- 방송 시작·종료, 상태·대기 큐 수·화면 채팅 수·현재 감정 표시
- 가상 채팅 직접 입력
- 큐 설정: 최소·최대 응답 대기 시간, 최대 큐 크기, 화면 채팅 표시 수
- 혼잣말 on/off와 간격, 같은 답변 금지 시간 설정
- LLM·TTS·기억 설정 패널과 호출 통계 표시
- 표정 8개·모션 4개 테스트 버튼. 방송 시작 전에도 실행되며 순번으로 중복 실행을 막는다
- 서버 연결 끊김을 배너로 표시하고 복구 시 자동 해제한다

### 1.6 채팅 큐와 응답 라우팅

- 메모리 큐에 채팅을 쌓고 5~10초 랜덤 지연 후 처리한다. 질문 채팅을 우선 선택한다
- 큐 최대 크기 제한, 공백 제거 정규화 후 중복 채팅 차단, 세션 시작 시 초기화. 중복은 `duplicateWindowMinutes`(기본 5분) 창 안에서만 보며 창이 지난 기록은 지운다. 창은 시청자 구분 없이 하나다
- 발화권을 명시적으로 관리해 답변과 혼잣말이 겹치지 않는다
- 같은 답변 문장 재사용 금지. 후보가 모두 쿨다운이면 가장 오래전에 쓴 문장을 선택한다
- 채팅이 없을 때 실행되는 혼잣말. 대기 중 채팅이 들어오면 취소하고 채팅에 먼저 반응한다
- 규칙 7종(인사·칭찬·위로·음악·게임·질문·기본), 규칙마다 문장 3개 랜덤 선택
- 응답 라우팅 3단: 규칙 → LLM → 실패 시 규칙 폴백. 질문 규칙은 `llmPreferred` 표시로 LLM에 양보한다
- **세션 세대(generation) 기반 경합 제어.** 비동기 LLM·TTS 결과가 도착했을 때 호출 시점의 세대와 현재 세대가 다르면 폐기한다. 이전 세션의 답변이 새 세션에 표시되지 않는다

### 1.7 안전성

- 정치·의료·법률·투자·개인정보·위험 요청은 LLM 호출 전에 차단하고 무반응 처리한다
- 프롬프트 공격과 시스템 메시지 요구도 동일하게 사전 차단한다
- LLM 출력은 감정·모션 allowlist를 포함한 6단계 검증을 통과해야만 실행된다
- 서버가 API 경계(`/api/live2d/test`)에서도 같은 allowlist를 강제한다. 경로 조작 문자열은 400으로 거부한다
- API 키는 `AES-256-GCM` + `scryptSync(사용자명@호스트명)` 파생 키로 암호화 저장한다. `enc.v1:` 접두사를 붙인다. 평문으로 남아 있던 LLM 키는 읽는 즉시 암호문으로 재저장되고 복호화 실패 시 경고 로그를 남긴다. ElevenLabs 키는 복호화만 하고 재저장·경고는 하지 않는다
- 키는 어떤 GET 응답에도 포함되지 않고 `hasApiKey` 불리언만 나간다. OBS 비밀번호는 환경변수 전용이다
- Vite 커스텀 플러그인이 비공개 자산 서빙 시 상위 경로 접근을 차단한다
- 위협 모델의 한계: 같은 머신에서 코드를 실행할 수 있으면 복호화도 가능하다. 파일 유출과 실수로 인한 공유를 막는 수준이다

### 1.8 Live2D 렌더링

- Cubism SDK for Web 5-r.5 연동. Core를 `<script>`로 동적 로드한 뒤 샘플 델리게이트를 Vite 별칭으로 import한다
- WebGL2 캔버스를 방송 화면 레이어에 삽입하고 투명 배경 처리로 React 레이어가 뒤에 보이게 한다
- 상반신 구도용 확대·이동 상수 도입. 채팅 패널과 겹치지 않으며 말풍선을 캐릭터 컬럼 중앙에 정렬한다
- 샘플의 교실 배경과 기어 아이콘 제거
- `packages/live2d`는 순수 매핑 레이어다. Cubism 코드 없이 표정 8종·모션 4종 allowlist, 감정→표정·모션 매핑, LLM용 모션 한국어 설명만 담당한다

### 1.9 표정·모션 실행

- 감정→표정 변환, 응답 actions→모션 선택, 양쪽 모두 allowlist 검증
- **표정·모션 짝 구조 대응.** 이 모델은 표정 파일이 효과를 켜는 스위치이고 모션 파일이 그 효과의 애니메이션을 돌린다. 모션 실행 시 짝 표정을 함께 켠다 (5절 참조)
- 기본 상태는 표정 해제다. 감정 지속 시간이 지나면 기본 상태로 복귀하고 방송 종료 시에도 초기화한다
- 표정 없는 감정 허용. `calm`·`curious`는 표정을 켜지 않고 기본 얼굴을 유지한다
- 같은 모션 반복 요청은 무시한다

### 1.10 시선과 립싱크

- SDK 샘플을 패치해 `lookAt()`과 `setManualLipSync()`를 추가했다. 방송 로직이 시선과 입을 직접 지정한다
- 마우스 추종 동작은 제거했다. 커서를 따라 시선과 몸이 움직이지 않는다
- 프레임레이트 독립 보간: `ratio = 1 - exp(-2.5 * dt)` 지수 감쇠로 60Hz와 144Hz에서 동일한 속도를 보장한다
- 연출 레이어: idle 시 1.1~3.2초마다 랜덤 응시, 새 채팅에 60% 확률로만 반응, 응시 각도와 시간을 매번 다르게 잡고, 채팅을 본 뒤에는 정면이 아니라 idle 흐름으로 복귀한다
- 립싱크 2종. 음성이 있으면 WebAudio `AnalyserNode` RMS 기반 실시간, 없으면 글자수 x 78ms 사인파 + jitter로 자동 전환한다
- SDK UpdateScheduler가 파라미터를 덮어쓰지 않도록 `onLateUpdate` 직후·`_model.update()` 직전 지점에 주입한다

### 1.11 외부 LLM

- 교체 가능한 `LlmAdapter` 인터페이스와 프로바이더 레지스트리
- **OpenAI 어댑터**: Chat Completions + Structured Outputs(`json_schema`, `strict: true`)로 스키마를 강제한다. 실 API 환경에서 검증 완료
- 스트리밍은 쓰지 않는다. 단발 `fetch` + `AbortController` 8초 타임아웃
- 출력 검증 6단계: JSON 파싱 → reply 길이 → 감정 allowlist → intensity/duration 범위 → 모션 allowlist → layer/priority
- 회로 차단기. 연속 실패가 기준에 닿으면 회로를 열어 호출을 끊고 방송은 규칙 문장으로 끊김 없이 이어진다. cooldown 후 자동 복귀
- 호출 수·실패 수·검증 실패 수·평균 지연 기록. 평균 지연 약 1.5~2.5초
- 프롬프트는 7계층으로 쌓는다: 공통 페르소나 → 모드별 대화 정책 → 세션 정보 → 기억 → 최근 대화 문맥 → 입력 → 출력 규칙. 고정 계층(페르소나·정책·출력 규칙과 모션 한국어 설명)은 system, 턴마다 바뀌는 계층(`[방송 상황]` → `[지금까지의 방송]` → `[기억]` → `[참고 정보]` → `[최근 대화]` → `[답변할 채팅]`)은 user 메시지에 넣는다. 계층 분리 이후의 실제 LLM 답변은 아직 확인하지 않았다(미검증). 프롬프트 구성은 단위 테스트와 통합 검사로만 확인했다
- 페르소나와 대화 정책 문장은 `packages/character`가 갖는다. 대화 모드는 `broadcast`와 `companion` 두 가지이며 서버는 `broadcast`만 쓴다. `companion` 정책은 프롬프트를 만들 수만 있는 초안이고 1:1 대화 API·앱은 없다. 설정 원본과 출처는 [캐릭터 바이블](./content/character-bible.md)에 있다
- 모션 이름이 병음이라 이름만으로는 모델이 의미를 파악하지 못한다. 한국어 설명 주입 후 모션 선택률이 0/6에서 6/6으로 바뀌었다
- 방송 종료 시 같은 어댑터에 프롬프트·스키마를 교체 주입해 대화 요약과 하이라이트를 생성한다
- 미지원 프로바이더 지정은 400으로 거부한다

### 1.12 장기 기억

- 저장소는 `data/memories.json` 단일 JSON 파일 + 인메모리 배열이다. SQLite도 벡터DB도 쓰지 않는다
- 하이브리드 검색. 코사인 유사도를 직접 구현하고 `similarity + importance * 0.05` 스코어로 정렬한 뒤 `minSimilarity` 필터와 top-K를 적용한다. 최종 활용 판단은 답변 LLM이 프롬프트 안에서 한다
- **우아한 성능 저하.** 임베딩 키가 없거나 호출이 실패하면 예외를 던지지 않고 중요도·최신순 정렬로 자동 강등된다. 저장 시 임베딩 실패도 저장 자체를 막지 않는다
- 교체 가능한 `EmbeddingProvider` 인터페이스. 현재 구현은 OpenAI 1536차원
- 방송 종료 시 대화에서 규칙 기반 정규식으로 기억 후보를 추출한다. 취향·경험 표현만 대상이고 단순 인사는 제외한다
- 위험 주제와 개인정보는 추출 단계와 저장 직전 두 번 차단한다. 요약도 저장 직전 재검사한다
- 같은 문장이 재등장하면 새로 만들지 않고 `repeatCount++`, `importance +0.1`, 수명 연장으로 처리한다. TTL 경과 시 자동 만료
- 지난 대화를 묻는 채팅은 규칙을 건너뛰고 LLM으로 전달한다
- 관리자에서 기억 목록 조회(공개 범위·소유자 표시), 개별·전체 삭제, 사용 여부·전달 개수·최소 유사도·보관 기간 설정
- **공개 범위와 소유자.** 기억마다 `scope`(`character`/`broadcast`/`private`)와 선택적 `ownerId`를 둔다. 검색은 접근 정보(방송의 말한 시청자, 또는 1:1 사용자)를 반드시 받고, 규칙표에 맞는 기억만 남긴 **뒤에** 유사도 순위와 폴백 정렬을 계산한다. 규칙표에 없는 조합과 알 수 없는 `scope`는 제외한다(fail closed)
- 방송 기억 추출은 소유자를 확정할 수 있는 발언만 대상으로 한다. 익명 발언은 후보가 되지 않고, 방송 요약·하이라이트는 소유자 없는 `broadcast` 기억이 된다. 같은 문장이라도 `scope`나 소유자가 다르면 합치지 않는다
- 파일 형식은 `{ version: 2, records }`다. 예전 형식은 서버가 기억을 처음 읽을 때 옮긴다. 소유자가 불명확한 기억(`virtual-viewer`, 소유자 없는 시청자 기억 등)은 지우고, 옮기기 전 원본을 `memories.v1-backup-<시각>.json`으로 같은 디렉터리에 남긴다. 변환·삭제 건수는 서버 로그에 남는다
- **1:1 개인 기억(`private`)은 스토어 지원만 있다.** 저장 형식, 검색 규칙, 소유자별 일괄 삭제(`removeByOwner`)까지 준비되어 있고 단위 검사로 확인했다. 1:1 대화 모드와 개인 기억을 만드는 경로는 아직 없다(Phase 4). `character` 기억도 검색 규칙만 있고 만드는 경로는 없다
- 단위 검사 `npm run test:unit`(접근 규칙표 전 칸, 두 검색 경로의 필터, 마이그레이션, 추출, 병합 키)과 통합 검사 `tools/test/isolation.mjs`(시청자 A의 기억이 B 채팅의 LLM 요청에 들어가지 않는지)가 이 동작을 확인한다
- 검색 방식을 하이브리드로 정한 배경은 [설계 결정 기록](./decisions.md)을, 공개 범위와 삭제 정책은 ADR-013을 참조한다

### 1.13 TTS와 음성 립싱크

- **OpenAI 음성 합성 검증 완료.** LLM과 같은 키를 쓴다. 목소리 6종, 모델 `tts-1`/`tts-1-hd`, 속도 0.25~4.0
- 서버에서만 합성한다. API 키가 브라우저로 나가지 않는다
- 합성 결과를 메모리에 최근 30건까지 삽입 순서(FIFO)로 캐시하고 `/api/tts/{id}`로 mp3를 내보낸다
- 음성을 먼저 만든 뒤 말풍선을 띄워 소리와 자막이 같이 시작된다. 답변의 생성(LLM+TTS)은 5~10초 연출 대기와 병렬로 돌아, 생성이 대기보다 짧으면 음성 때문에 늘어나는 지연이 없다. 혼잣말에도 음성을 붙인다
- 합성 실패 시 소리 없이 방송을 이어간다. 지원하지 않는 음성 업체는 400으로 거부한다. **목소리 이름은 검사하지 않는다**(3.2절)
- 브라우저 자동 재생이 막히면 `소리 켜기` 버튼을 노출한다
- 업체 교체 가능한 구조. 방송 로직은 어느 업체를 쓰는지 알지 못한다. 업체별 키를 따로 관리하고 같은 방식으로 암호화한다

### 1.14 OBS 송출

- 의존성 0개의 OBS WebSocket v5 클라이언트를 직접 구현했다. op0 Hello의 salt/challenge SHA256 인증 핸드셰이크와 requestId 기반 Promise 매칭 포함
- 씬 생성 → 브라우저 소스 생성·갱신 → 캔버스 1920x1080 설정 → 소스 트랜스폼 초기화까지 자동화한다
- 송출 화면 스크린샷 저장 스크립트 제공
- 실제 송출에서 모델·채팅·말풍선·표정·모션 동작을 확인했다

### 1.15 방송 문맥 확장과 응답 지연 단축

2026-09-01에 들어간 기능이다. **가짜 OpenAI API에 실제 서버를 붙인 통합 검사로만 확인했고 실 API로는 확인하지 않았다**(2절).

- **방송 중 누적 요약.** 최근 대화 창(발언 10개, 채팅 5건 분량) 밖으로 밀려난 흐름을 `rollingSummaryTurns`(기본 10, 하한 4)마다 이전 요약과 합쳐 한 문단으로 접고 `[지금까지의 방송]`으로 넣는다. 요약이 늦게 도착해도 세션이 바뀌었으면 버린다
- **키워드 매크로.** `data/macros.json`의 키워드가 채팅에 나오면 설명을 `durationTurns` 동안 `[참고 정보]`에 넣는다. 동시 5개까지. 관리자 API로 다시 읽을 수 있다. 예시는 [macros.example.json](./macros.example.json)
- **방송 상황 문장.** 경과 분과 답변 수를 서버가 계산해 `[방송 상황]`으로 넣는다
- **대기·생성 병렬화.** 5~10초 연출 대기와 LLM·TTS 생성을 `Promise.all`로 겹친다. 통합 검사에서 직렬이면 약 9.8초였을 경우가 약 6.0초로 끝난다. 대기 중 들어온 채팅은 이번 차례의 후보에서 빠진다
- **기억 없음 명시.** 꺼낸 기억이 없으면 `[기억]` 계층에 지어내지 말라는 문장을 넣는다

## 3. 미완성·알려진 한계

### 3.1 기능적 한계

| 항목 | 내용 |
|---|---|
| 치지직·유튜브 연동 | 연동 코드가 존재하지 않는다. 전체 코드에서 발견되는 것은 `ChatSource` 타입 유니온의 `"chzzk"` 문자열뿐이며 실제 생성 값은 항상 `"manual"`이다 |
| STT | 마이크·음성인식 관련 코드가 0건이다 |
| Electron 방송 창 | 미지원. 방송 화면은 브라우저 전용이다 |
| 레이아웃 B와 레이아웃 전환 | [요구사항](./requirements.md)의 레이아웃 B(왼쪽 콘텐츠·오른쪽 위 채팅·오른쪽 아래 보리)와 방송 중 레이아웃 전환이 통째로 미구현이다. `packages/shared`의 `layout`은 타입에만 있고 서버 상태는 항상 `"chat"`으로 고정된다. 전환용 API도 관리자 UI도 페이드 효과도 없다. 방송 화면이 그릴 수 있는 것은 레이아웃 A 하나뿐이다 |
| 채팅 큐 고급 선별 | [요구사항](./requirements.md)이 정의한 유사 채팅 그룹화, LLM 주제 묶기와 그룹 수 전달, 주제 고착 방지가 모두 미구현이다. 서버에 그룹화·주제 추적 코드가 없다. 최근 N개 우선(`preferredRecentCount`)과 오래된 채팅 만료(`messageTtlSeconds`)도 큐 설정에 두 키 자체가 없어 적용되지 않는다. 현재 선별은 질문 우선과 중복 차단까지다 |
| 관리자 화면 일부 미구현 | [요구사항](./requirements.md)의 1차 관리자 기능 중 규칙 기반 답변 수정, 미처리 채팅 확인, 오류 리포트 확인, LLM 연결 테스트, 효과음 설정 패널이 관리자 UI에 없다. `unprocessedCount`는 서버 상태에만 있고 화면에 표시되지 않는다. 요구사항이 말하는 단일 실행 진입점(관리자 앱 하나를 실행하면 백엔드와 방송 화면도 함께 시작)도 없다. `dev:admin`은 관리자 앱만 띄우며 셋을 함께 기동하는 경로는 루트 `npm run dev`뿐이다 |
| 시청자 식별 | 기억 소유자는 닉네임에서 만든 `local:닉네임`이다. 인증이 없으므로 다른 사람이 같은 닉네임을 입력하면 그 시청자의 기억이 답변 문맥에 들어간다. 플랫폼 계정 ID 연동 전까지의 한계다 |
| 1:1 대화 모드 | 없다. `packages/character`의 `companion` 정책 초안과 프롬프트 조립만 있고 1:1 대화 API·세션·앱은 없다(6절 Phase 3~5) |
| 1:1 개인 기억 | 스토어와 검색 규칙만 있고 생성 경로는 없다(Phase 4). 방송 기억과 1:1 사용자를 잇는 계정 연동도 범위 밖이다 |
| 효과음·시청자용 오류 알림 | 요구사항에 표시 시간·알림 큐 최대치·우선순위까지 정의되어 있으나 코드가 없다 |
| 배경 일러스트 교체 | 미구현. 보라색 그라데이션을 하드코딩한다. Live2D 캔버스만 투명하고 화면 전체는 불투명하므로, OBS 오버레이로 쓰려면 `.broadcast-shell` 배경을 투명하게 바꿔야 한다 |
| 기억 기반 혼잣말 | 미연결. 혼잣말은 여전히 하드코딩된 7문장 기반이다 |
| 원문 채팅 로그 저장 | 없다. 메모리에만 있고 파일로 남기지 않는다. 요구사항의 원문 로그 수동 삭제 정책을 적용하려면 저장이 선행되어야 한다 |
| 모순된 취향 처리 | 없다. 같은 문장만 합치고 모순 여부는 판단하지 않는다 |
| gemini 프로바이더 | 타입에만 존재하고 팩토리가 `null`이라 `supportedProviders`에서 자동 제외된다. 미구현이다 |
| 대기 모션 | 없다. 이 모델의 모션 4개는 모두 짝 표정이 필요한 효과 애니메이션이라 대기용으로 쓸 수 없다. 대기 중 눈 깜빡임과 호흡은 SDK가 처리한다 |
| TTS 스트리밍 | 미지원. 음성을 다 만든 뒤 말풍선을 띄운다. 소리와 자막을 맞추기 위한 선택이다. 생성은 연출 대기와 병렬이라 생성(LLM+TTS)이 대기보다 짧으면 추가 지연이 없고, 길면 그 차이만큼 늦어진다 |
| 음성 파일 영속화 | 없다. 메모리 캐시 30건이며 서버를 재시작하면 사라진다 |
| 목소리 적합성 | 이 프로젝트에서 시험해 본 범위에서는 OpenAI 목소리 6종이 모두 실제 사람 톤에 가깝게 들렸고, 한국어 대사에서도 원하는 애니메이션풍 인상이 나오지 않았다. 캐릭터 콘셉트와 맞지 않는다고 판단해 사용하지 않는다 |
| 립싱크 정밀도 | 파형 크기로 입을 벌리므로 소리 크기에는 맞지만 모음별 입 모양은 구분하지 않는다. 이 모델은 `ParamMouthOpenY` 하나만 립싱크 대상으로 등록되어 있다 |
| API 키 암호화 한계 | OS 키체인을 쓰려면 Electron `safeStorage`가 필요한데 서버가 별도 프로세스라 직접 사용할 수 없다. 관리자 앱이 키를 대신 관리하고 서버에 전달하는 구조로 바꿔야 한다 |
| 채팅 화면 LAN 접속 | 불가. API 서버·방송 화면 dev·preview가 모두 `127.0.0.1`에 바인딩되고 바꾸는 옵션도 없다. 바인딩만 넓히면 Vite 프록시가 `/api` 전체를 넘기므로 인증 없는 관리 API까지 LAN에 열린다. 채팅 화면만 열려면 `/api/chat`·`/api/state`만 통과시키는 경로와 API 보안 강화(6절 Phase 4 선행 조건)가 먼저 필요하다 |

### 3.3 캐릭터 설계 미결정

`kuqi`(울음)·`shengqi`(화남)·`wuyu`(어이없음)는 규칙 응답에서 나오지 않는다. 각각 `crying`·`angry`·`awkward` 감정에 매핑되어 있으나 그 감정을 발생시키는 규칙이 없다. **기술적 미해결이 아니라 캐릭터가 화내거나 우는 상황을 어떻게 다룰지 정하지 않은 설계 미결정 사항이다.** 관리자 테스트 버튼으로는 전부 정상 실행된다.

다만 LLM에게 넘기는 모션 설명은 `kuqi`·`shengqi`를 쓸 상황을 이미 안내하고 있어, LLM 답변에서는 울음·화남 모션이 나올 수 있다. 이 충돌과 1:1 대화 정책의 미결정 항목은 [캐릭터 바이블](./content/character-bible.md) 6.3절과 [페르소나 가이드라인](./content/persona-guidelines.md) 4.1절에 `검토 필요`로 모아 두었다.

## 5. 알려진 함정과 해결

재사용 가치가 있는 기술 노트다. 구현 과정에서 실제로 발생한 문제와 원인이다.

**Vite dev 프록시는 백엔드가 죽어도 5xx를 반환한다.** 방송 시작 버튼이 반응하지 않던 원인은 API 서버가 포트 충돌로 종료된 상태였고 관리자 화면이 그 사실을 표시하지 않았기 때문이다. 프록시가 응답 자체는 돌려주므로 `fetch` 예외만으로는 서버 다운을 판단할 수 없다. **상태 코드 500 이상을 함께 확인해야 한다.** 이후 연결 실패와 서버 오류를 구분해 배너로 표시하도록 고쳤다. 포트 충돌 대응은 [운영 가이드](./operations.md)를 참조한다.

**이 모델은 표정과 모션이 짝 구조다.** 표정 파일이 효과를 켜는 스위치이고 모션 파일이 그 효과의 애니메이션을 돌린다. 표정 없이 모션만 실행하면 화면에 아무 변화가 없다. `shengqi`의 파라미터를 0.5초 간격으로 측정해 확인했다.

| 실행 내용 | Param66 (표정) | Param68 (모션) |
|---|---|---|
| 표정만 | 1 고정 | 0.204 고정 |
| 표정 + 모션 | 1 고정 | 0.589 → 0.238 → 0.898 → 0.600 → 0.287 → 0.953 |

표정만으로는 효과가 한 위치에 멈춰 있고 모션까지 실행해야 값이 계속 진동한다. **정지 화면(스크린샷)으로는 둘을 구분할 수 없고 시간축 파라미터 변화로만 관측된다.** 모션 실행 시 짝 표정을 함께 켜도록 구현했다.

**React StrictMode 이중 마운트가 전역 싱글톤을 파손한다.** Live2D 렌더러는 전역 싱글톤인데 StrictMode가 effect를 두 번 실행해 캔버스가 두 개 생기고 내부 서브델리게이트 배열이 빈 채로 남았다. 동적 import 콜백에서 취소 여부를 확인해 초기화가 한 번만 일어나도록 고쳤다.

**Electron 흰 화면의 원인이 Electron이 아닐 수 있다.** 관리자 창이 로딩 문구에 멈춰 있던 원인은 컴포넌트를 `export default`만 하고 `createRoot(...).render(...)`를 호출하지 않은 것이었다. 브라우저에서 열어도 같은 증상이므로 Electron 계층을 의심하기 전에 브라우저로 먼저 확인하는 편이 빠르다.

**SDK 샘플의 모델 경로가 중복 조합된다.** 요청 경로가 `ResourcesPath + ModelDir + '/'`로 조합되는데 `ResourcesPath`에 모델 디렉터리명이 이미 포함되어 404가 발생했다. 함께 발견된 것 — Vite 자산 브리지의 경로 치환이 백슬래시 2개를 찾고 있어 Windows 경로가 변환되지 않던 버그, 모델에 존재하지 않는 모션 그룹 이름, 기어 스프라이트 부재 시 클릭 크래시.

**비동기 결과는 세션 상태만으로 유효성을 판단할 수 없다.** LLM(8초)과 TTS(15초) 응답이 도착하기 전에 방송이 종료·재시작될 수 있는데 `state.status`는 다시 `live`가 되므로 이전 세션인지 구분되지 않는다. 실제로 이전 세션의 답변이 새 세션 화면에 표시됐다. 호출 시점의 `sessionGeneration` 정수를 캡처해 두고 콜백에서 세대가 다르면 결과를 폐기하는 방식으로 해결했다.

**`tsx watch` 재시작 시 EADDRINUSE가 발생한다.** 이전 프로세스가 포트를 놓기 전에 새 프로세스가 기동해 종료됐다. 1초 간격 최대 10회 재시도로 해결했다.

**LLM에 병음 식별자만 주면 모션을 고르지 못한다.** 모션 이름이 병음이라 이름만으로는 모델이 의미를 파악할 수 없었다. 한국어 설명을 함께 전달하자 6건 중 6건에서 모션이 선택됐다. 이전에는 0건이었다.

## 6. 남은 작업 / 향후 범위

Bori 2.0(방송 모드 + 1:1 companion 모드)의 단계 번호는 사용자 지시서를 따른다. 각 단계의 구조와 완료 기준은 [아키텍처 v2](./architecture-v2.md) 10절에 있다.

### 완료

- **Phase 1 기억 격리** — main 병합. 공개 범위(`character`/`broadcast`/`private`)와 `ownerId`, 접근 규칙표, fail closed 검색, 소유자 불명 기억 삭제 마이그레이션(백업 유지). 1.12절
- **Phase 2 캐릭터 페르소나** — main 병합. `packages/character`, 프롬프트 7계층, `LlmRequest.mode`. 1.11절. 캐릭터 설정의 `검토 필요` 항목은 그대로 둔다
- **방송 상태 닉네임 노출 수정** — main 병합. `/api/state`에 `VisibleChat`만 싣는다. 1.4절
- **루트 typecheck 범위 보완** — 8개 워크스페이스. 3.2절

### Phase 3 — 공통 대화 엔진

진행 중(별도 PR).

1. `makeResponse`·`recordTurn`·누적 요약·매크로를 서버 전역 상태에서 대화 세션 단위 엔진(`apps/server/src/conversation/`)으로 옮긴다. 방송 동작은 바꾸지 않는다
2. 후속 정리: 방송 코드 분리. `index.ts`에서 큐·발화권·세션 세대·혼잣말과 HTTP 라우팅을 떼어 낸다
3. 후속 정리: 죽은 코드·죽은 타입 필드·선언만 된 의존성·낡은 주석(3.2절)

### Phase 4 — 1:1 대화 API

계획. **선행 조건: API 보안 강화.** 1:1 API를 보안 경계 없이 연 상태가 없도록 아래를 먼저 병합한다.

1. 선행: CORS 출처 제한, 로컬 토큰, 요청 본문 크기 제한, 설정값 검증(`PATCH /api/settings`·`/api/memory`·`/api/tts`), 목소리 이름 검증
2. `/api/companion/*`, 1:1 세션 관리, 모드별 LLM 클라이언트(회로·통계 분리)
3. 1:1 개인 기억(`private`) 생성 경로 연결. 저장 형식과 검색 규칙은 준비되어 있다

### Phase 밖 — 기존 과제

단계에 넣지 않은 과제다. 번호는 이전 판의 우선순위를 유지하지 않는다.

- TTS 자격 증명을 업체별로 분리(3.2절)
- 표정 표시 이름 실제 동작 확인 후 확정
- 캐릭터에 맞는 한국어 목소리 확보. CLOVA Voice, Typecast, Supertone, 음성 클로닝을 검토한다
- 효과음 출력과 시청자용 오류 알림 표시. 요구사항에 있으나 미구현 상태다
- 출력 검증기·규칙 응답 단위 검사, CI 도입
- 원문 채팅 로그 저장과 수동 삭제. 요구사항 정책 적용의 선행 조건이다
- TTS 스트리밍 합성으로 응답 지연 단축
- 치지직 실제 채팅 연동. MVP 범위 밖이다
- Electron 방송 화면 창 지원
- 배경 일러스트 교체 기능과 OBS 오버레이용 투명 배경 모드
- 기억 기반 혼잣말 연결
- 모순된 취향 처리
- 폴링을 WebSocket 또는 SSE로 교체
- 이터널리턴 API 연동. 게임 지식 RAG 용도다

이전 판의 "`duplicateWindowMinutes` 설정과 실제 동작 일치시키기"는 이미 코드가 창 기준으로 동작해 삭제했다(1.6절). "루트 `typecheck`에 live2d·llm·memory 편입"은 완료했다.

## 7. 구현 원칙

- 초기 버전은 규칙 기반으로 동작하고 LLM은 교체 가능한 어댑터로 연결한다
- AI가 임의의 Live2D 동작을 생성하는 것이 아니라 등록된 표정·모션 중에서 선택한다
- 모델 자산과 방송 로직을 분리한다
- 관리자 설정으로 변경 가능한 값은 하드코딩하지 않는다
- 오류가 발생해도 세션을 유지하고 오류는 관리자에게만 표시한다
- 구매 모델 파일과 Cubism SDK Core는 저장소에 포함하지 않는다
- API 키는 코드에 직접 작성하지 않는다
- 위험 주제와 프롬프트 공격은 LLM 호출 전에 차단하고, LLM 출력은 허용된 감정·모션·형식만 통과시킨다
- 방송 화면에 시청자 닉네임을 표시하지 않으며 원본 채팅 로그와 장기 기억 데이터는 로컬에만 저장한다
